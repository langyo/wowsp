# AI モデルの配布: Hugging Face チャネルとマルチプロバイダーミラー（設計契約）

> ステータス: DRAFT —— `feat/ai-models` ウェーブの実装契約。
> スコープ: 組み込みの意思決定/スコアリングモデル（ONNX 重み、艦船属性
> ルーティングテーブル、マップごとの地形 LOS ラスター）と、それらの
> 学習/デプロイ用スクリプトを公開の Hugging Face モデルリポジトリへ公開し、
> 新しい署名付き `ai` リソースチャネルを通じてファイル単位のダウンロードで
> クライアントへ配信する。さらに、GitHub 専用だったミラーラダーを、
> すべてのダウンロード可能リソースで共有されるプロバイダー認識型のミラー
> コンテキストへ一般化する。
>
> 範囲外: 凍結済みのアプリ更新チャネル、`res-latest` リソースパック
> （GitHub Releases のまま）、学習パイプライン自体、およびリプレイ
> データセットの公開。

## 1. 課題と目標

組み込みの意思決定モデル（ONNX の射撃/移動スコアリングヘッド、属性ルーティングされた
アドバイスモデル、任意の魚雷モデル、ルーティングテーブル、マップごとの地形視線（LOS）
ラスター）には**配布チャネルが一切存在しない**。これらは `scripts/experiments/out/`
配下の git 管理外の学習出力として存在し、インストール済みの `<cache>/decisions`
パックは手作業でコピーされたディレクトリで、アプリはその内容を一覧表示してクリアする
ことしかできない。公開スクリプトもマニフェストもダイジェストもダウンローダーも
バージョンスタンプもカバレッジ保証も存在しない —— 現状、既知のマップ ID 96 個のうち
35 個だけが LOS ラスターを持ち、インストール済みの 2 モデルは古く、サイズは現行の
fp32 エクスポートのおよそ半分で、アドバイス/魚雷のスロットは単に空である。

一方、アプリはよりリッチなパックを配信する方法をすでに知っている。`res-latest`
リソースパックはこのリポジトリから公開され、中国本土のネットワーク向けに ghproxy
方式のラダーでミラーリングされ、公式の sha256 ダイジェストに対して検証され、
アトミックに適用される。意思決定モデルのチャネルも、1.3 GB のリソースパックが持つ
制約を継承することなく、同じエンジニアリング水準に到達すべきである。

目標:

1. **単一の公開・再現可能な成果物。** すべてのモデルリリースは、名前付きの
   リポジトリコミットからチェックイン済みのスクリプトによって生成され、学習/
   デプロイ用スクリプトとともに公開の Hugging Face モデルリポジトリへ公開される。
2. **アプリのリリースから独立した更新 —— ただし特徴量契約の範囲内。**
   再学習されたモデルは、その入力/特徴量スキーマが実行中の featurizer と一致する
   限り、新しいアプリビルドなしでインストール済みクライアントへ届く。スキーマ
   変更は定義上、アプリのリリースである。
3. **実行前の完全性。** モデルファイルは ONNX Runtime によって解析・実行される
   ため、チャネルはフェイルクローズドである。署名付きマニフェストが各ファイルの
   sha256 と Hugging Face のコミットをピン留めし、未署名または不一致のペイロードは
   決してインストールされない。
4. **中国本土からの到達性。** ランタイムのラダーは、`huggingface.co` が到達不能な
   環境（メンテナのネットワークで検証済み）でも、単一のサードパーティミラーを
   ハードコードすることなく動作しなければならない。
5. **単一のミラーフレームワーク。** GitHub、Hugging Face、そして（将来は）
   ModelScope が、プロバイダー認識型の単一のコンテキスト —— 候補の書き換え、
   プローブ、ヘルス/スティッキー選択、ドリフト検査済みエンドポイントリスト ——
   を共有する。ghproxy プレフィックスリストを 5 つ複製するのではなく。
6. **ツリー内に秘密情報を置かない。** Hugging Face の認証情報は環境または
   ユーザートークンストアに置く。追跡対象ファイルには決して置かない。

## 2. 現状

| 領域 | 現状 | 結果 |
| --- | --- | --- |
| モデルの公開 | なし | 手作業のコピー以外に、ユーザーへモデルを届ける手段がない |
| インストール済みパック | `<LOCALAPPDATA>/WoWSP/decisions`、手作業でコピー | 古い/部分的な状態。スタンプなし。世代違いのモデルを検出できない |
| モデルのロード | `decision_serve` ラダー env -> パックスロット -> 開発出力。`ship_attrs` はコンパイル時の `include_str!` テーブルを使用 | ルーティングテーブルの変更にアプリのリリースが必要。「パックが埋め込みテーブルを上書きする」というコメントは実装されていない |
| リソースパック | GitHub の `res-latest` + デルタチェーン + リレー署名付きダイジェスト | 成熟しており、現状のまま |
| ミラーラダー | GitHub 専用のホストリストに ghproxy プレフィックスを連結。Rust、Cargo メタデータ、Python、ウェブサイト、webui モック、リレー CSP にコピーが存在 | `huggingface.co` を前面に置けない。ドリフトは 1 コピー分しかテストされていない |
| モバイル | ONNX Runtime がデフォルト機能のため、Android/iOS ビルドは ONNX を同梱する。decisions パックは同梱されない | モバイルも同じチャネルの恩恵を受けられる |
| レジストリ行 | `decisions-pack`、チャネルは空、トリガーは `manual` | チェック/ダウンロードボタンなし、フレッシュネス台帳のエントリなし |

したがってこのウェーブは**チャネルを新設する**のであって、既存のチャネルを移行する
のではない。

## 3. アーキテクチャ概要

3 つのレイヤがあり、それぞれに 1 つの役割がある:

```text
  GitHub repo (source of truth)
      |  python scripts/publish_ai_models.py  (hash -> sign -> upload)
      v
  Hugging Face model repo  wowsp-ai  (generated release artifact + scripts snapshot)
      |  signed manifest.json + per-file resolve/<commit-sha>/<path>
      v
  client  commands/ai_pack.rs  --->  commands/mirror/ (MirrorContext)
      |      per-file download via download_hub        GitHub | Hugging Face | ModelScope
      v
  <cache>/decisions  (fire/move/advice/torpedo + attrs + <map>/terrain_los.npz)
```

| 決定 | 選択 | 理由 |
| --- | --- | --- |
| ダウンロード元 | v1 では Hugging Face のみ（組み込みの `hf-mirror.com` を加える）。GitHub Release のフォールバックと ModelScope は後のプロバイダー | 検証すべき公開経路が 1 本で済む。ミラーコンテキストによりプロバイダーの追加は安価になる |
| マニフェストの信頼アンカー | 既存のピン留めされた Ed25519 鍵と `seq` ラチェットを使った自己署名マニフェスト | Hugging Face はアセット単位の公式ダイジェストを公開しない。リレーのダイジェストチャネルはモデルリリースごとにデプロイ手順を増やすだけで、追加の保証は得られない |
| 転送単位 | 成果物ごとに 1 ファイル、アトミックなステージングインストール | すべてのファイルが 10 MB 未満。増分更新が可能。ハブはすでにセグメント単位の進捗、sha256、上限、再開、キャンセルをサポートしている |
| ミラー選択 | コールドスタートヘッジング、パスごとのスティッキーエンドポイント、ヘルス用クールダウンを備えたプロバイダー認識型ラダー | 公式ホストは一部のユーザーにとって到達不能。ユーザーが列挙した決定的な順序は保存されなければならない |
| リソースパック | 変更なし、GitHub 専用 | 5.7k ファイル、デルタチェーン、GitHub アセットダイジェストのほうが適合し続ける |

## 4. Hugging Face リポジトリ

### 4.1 レイアウト

```text
wowsp-ai/                          public model repository (owner/repo TBD, see 11)
  README.md                        model card: purpose, provenance, metrics, file table, licence
  LICENSE                          Synthetic Source License 1.0 (same as the app repo)
  manifest.json                    signed runtime manifest (section 5)
  NOTICE.md                        game-data provenance and redistribution note (section 4.5)
  onnx/fire_model.onnx
  onnx/move_model.onnx
  onnx/advice_fire_model.onnx
  onnx/torpedo_model.onnx
  onnx-int8/                       optional quantized variants, never installed by default
  attrs/ship_attributes.json
  los/<mapId>/terrain_los.npz
  training/                        generated snapshot: scripts/experiments training/deployment scripts
  SOURCE.json                      {"repo","commit","generatedAt","tool":"scripts/publish_ai_models.py"}
```

`manifest.json` は、アプリがチャネルのエントリポイントとして扱う唯一のファイルで
ある。個々のファイルは、人間からも、モデルカードのファイル表からも個別に
ダウンロードできる。

### 4.2 ファイルサイズ規則

各リポジトリファイルは**10 MB 未満**に保たれるため、プレーンな Git blob として
格納される（`/resolve/` がバイト列を伴う 200 を返し、署名付き CDN リダイレクトも
xet 再構築もない）。LOS ラスターは現在、マップごとに 1 ファイルである（すべて上限を
大きく下回る）。将来のパックがファイル単位の上限を超える場合は、LOS を番号付き
バンドルに分割し、それぞれが上限未満に収まるようにする。パブリッシャーは 10 MB を
超えるステージングファイルを拒否し、違反パスを出力する。

### 4.3 リビジョンモデル

Hugging Face のリビジョンはコミットである。ブランチ/タグは移動できるが、コミット
SHA は移動できない。したがって公開は 2 つのコミットを使う:

1. 成果物ファイル（重み、attrs、LOS、スクリプトのスナップショット）を
   アップロードする -> コミット `A`;
2. `manifest.json`、`README.md`、`LICENSE`、`NOTICE.md`、`SOURCE.json` を、
   マニフェスト内に `"revision": "A"` を含めてアップロードする -> コミット `B`。

アプリはブランチヘッド（`main`）から `manifest.json` を取得し、その署名を検証して
から、すべてのファイルを `/{repo}/resolve/{A}/{path}` からダウンロードする ——
これは不変のピン留めである。古いマニフェストをキャッシュしたクライアントは、
`main` が進んでも古いコミットを使い続ける。注釈（`models-<seq>` タグ）は人間専用
である。

### 4.4 公開ワークフローと運用

`scripts/publish_ai_models.py`（`scripts/release_models.py` をモデルにしている）:

1. 入力を収集する（重み、`ship_attributes.json`、ベイク済み LOS ディレクトリ、
   指定コミットの `git archive` によるスクリプトスナップショット）。
2. すべてのファイルをハッシュし、署名付きマニフェストを構築し（第 5 節）、
   ツリーハッシュを計算する。
3. 成果物をアップロードし（コミット A）、次にマニフェストとドキュメントを
   アップロードする（コミット B、A にピン留め）。
4. リリースサマリー（seq、マニフェスト sha256、HF コミット、ファイル表）を
   出力する。`--dry-run` はアップロードを行わずにすべてのローカル手順を実行する。

**アカウント、トークン、リポジトリの作成。** Hugging Face には匿名の書き込み経路が
ない。公開にはアカウントと書き込みトークンが必要である。トークンは Web UI
（Settings -> Access Tokens。可能ならこのリポジトリの書き込みスコープに限定した
ファイングレイントークン）で作成し、`HF_TOKEN` または標準のユーザートークンストア
（`~/.cache/huggingface/token`）経由で供給する。リポジトリ自体は、スクリプトが
`huggingface_hub.create_repo`（REST `POST /api/repos/create`）で、Web UI で、
あるいは任意の `hf repo create` CLI で作成できる —— 3 つは等価であり、**CLI は
前提条件ではない**。パブリッシャーは `huggingface_hub` Python API を使う。これは
公式の `huggingface/hub-sync` GitHub Action がラップしているのと同じものである。
将来 CI レーンが同じスクリプトを、リポジトリシークレット（決して追跡されない）と
しての `HF_TOKEN` 付きで実行してもよい。

**ネットワークの現実。** 書き込みを受け付けるのは `huggingface.co` のみである。
中国本土からこのホストへ直接到達することはできない（検証済み: 接続タイムアウト）。
そのためローカルでの公開実行にはメンテナの HTTP(S) プロキシ（`HTTPS_PROXY`）が
必要か、公開を CI 上で実行する必要がある。ミラーは読み取り専用プロキシである。
ランタイムの読み取りにはプロキシ不要だが、書き込みには必要である。アップロード後の
検証はミラー経由で行える（7.8 節）。

**バージョニング。** `seq` は `manifest.json` に保存される厳密増加の公開カウンター
である（現在公開中のマニフェストの値を超えていない場合、パブリッシャーは警告を
出す）。`version` は UTC の公開タイムスタンプであり、内容の同一性は `treeSha256`
である（5.4 節）。

### 4.5 ドキュメントと来歴

- `README.md` はモデルカードである。各モデルが何をするか、featurizer の契約、
  `scripts/experiments/README.md` からの評価数値（該当する場合は
  auPRC/AUC/ECE/十分位リフト）、入出力テンソル形状、再現方法、正確な GitHub
  コミットへのリンク、ライセンスを記す。
- `SOURCE.json` はリポジトリ、コミット、生成時刻、正確なツリーハッシュを記録する
  ため、リリースされた成果物はコードへ追跡できる。
- `training/` は `scripts/experiments/` の**生成スナップショット**（スクリプト、
  ビルドヘルパー、研究ログ）である。モデルカードには、権威あるソースは記録された
  コミット時点の GitHub リポジトリであり、スナップショットを Hugging Face 上で
  編集してはならないと明記する。
- 生のリプレイコーパスは決して公開されない。それらはユーザー提供のセッションデータ
  である。モデルカードはコーパスの形状とフィルタリング/同意の根拠を集約的な表現で
  のみ記述する。
- `NOTICE.md` は、LOS ラスターが公開されたマップジオメトリからベイクされ、属性
  テーブルがゲームデータから導出されることを記録し、Synthetic Source License の
  開示要件を再掲する。重みはリプレイ由来の特徴量から学習される。これは公開
  `res-latest` チャネルがすでに配信しているのと同じデータクラスである。2 つ目の
  公開ホストへの公開はライセンスを変えないが、可視性は変えるため、明示的に言及する
  （第 11 節、決定 2）。

### 4.6 同期ポリシー

GitHub が唯一のソース・オブ・トゥルースである。Hugging Face は生成されたリリース
成果物であり、手作業の編集も、2 つ目の開発ブランチも、バック同期もない。モデルの
変更はこのリポジトリで始まり（学習スクリプト + パブリッシャーの入力にコミットされる
成果物）、その後メンテナがパブリッシャーを実行する。したがって 2 つのホスト間の
差異は、並行メンテナンスではなくコミットの来歴によって説明される。

## 5. 署名付きマニフェスト

### 5.1 例

```json
{
  "format": 1,
  "seq": 7,
  "version": "2026-11-08T14:22:03Z",
  "revision": "0123456789abcdef0123456789abcdef01234567",
  "source": { "repo": "langyo/wowsp", "commit": "89abcdef0123456789abcdef0123456789abcdef" },
  "resTreeSha256": "3f2a...",
  "files": [
    { "path": "fire_model.onnx", "sha256": "8ba9...", "size": 2592543,
      "kind": "fire-two-head", "featureSet": "fire-v2", "quant": "fp32" },
    { "path": "move_model.onnx", "sha256": "bc91...", "size": 2652542,
      "kind": "move-sectors-17", "featureSet": "move-v2", "quant": "fp32" },
    { "path": "advice_fire_model.onnx", "sha256": "b98f...", "size": 2595135,
      "kind": "advice-fire-attrs", "featureSet": "advice-e24", "quant": "fp32" },
    { "path": "torpedo_model.onnx", "sha256": "a7e3...", "size": 492411,
      "kind": "torpedo-three-head", "featureSet": "torpedo-e26d", "quant": "fp32" },
    { "path": "ship_attributes.json", "sha256": "2bbd...", "size": 261507 },
    { "path": "50_Gold_harbor/terrain_los.npz", "sha256": "9c1d...", "size": 172432 }
  ],
  "treeSha256": "d41d...",
  "metrics": { "fire": { "auprc": 0.32, "auc": 0.72 } },
  "key_id": "main",
  "sig": "MEUCIQ..."
}
```

### 5.2 フィールド

| フィールド | 意味 |
| --- | --- |
| `format` | マニフェストスキーマのバージョン（1） |
| `seq` | 厳密増加の公開カウンター。アプリは最後にインストールした値より小さい値を拒否する |
| `version` | UTC の公開タイムスタンプ。表示専用 |
| `revision` | リストされたファイルを正確に含む Hugging Face のコミット SHA |
| `source` | リリースの生成元である GitHub リポジトリ + コミット |
| `resTreeSha256` | LOS ラスターをベイクした対象のリソースパックのツリーハッシュ（任意。LOS を同梱しない場合は存在しない） |
| `files[].path` | `<cache>/decisions` 内の宛先パス。プレーンな相対パスで、セグメントを検証する（`[A-Za-z0-9._-]`、`..` 不可、セグメント内に区切り文字なし） |
| `files[].sha256` | 正確なバイト列の小文字 sha256 |
| `files[].size` | バイトサイズ。転送の下限/上限として使う |
| `files[].kind`, `featureSet`, `quant` | モデル契約のメタデータ。`.onnx` エントリでは必須、データファイルでは存在しない |
| `treeSha256` | 内容の同一性: ソートした `path\0sha256\n` 行に対する sha256（リソースパックと同一の式なので、同じツール群で両方をハッシュできる） |
| `metrics` | 学習レポートからコピーした表示用メタデータ |
| `key_id`, `sig` | Ed25519 署名レイヤー |

### 5.3 署名とアンチロールバック

署名は、**`sig` メンバーを除いた**マニフェストの正規化 JSON を対象とする ——
キーはソート済み、コンパクトな区切り文字、UTF-8。これは
`scripts/catalog_signing.py` がすでに実装し、アプリがコンパイル時にピン留めされた
公開鍵（`packages/app/tauri/res/keys/*.pub`）に対して検証するのと同じ正規形である。
署名は既存のリリースダイジェストの鍵セレモニーを再利用する。新しい鍵ペアは導入
しない。

アプリはフィールドを解析する前に署名を検証し、次に `seq` ラチェットを適用する。
ローカルに保存された値より seq が小さい認証済みマニフェストは拒否される
（リプレイ/ダウングレード対策）。したがってミラーは、最悪でも古い署名付き
マニフェストを再配信することしかできず、偽造は決してできない。マニフェスト取得の
失敗や不正な署名はこのチェックのハード失敗である —— ペイロードは実行可能な
モデル内容であるため、このチャネルには意図的に「検証されていないミラー
マニフェストを受け入れる」フォールバックが**存在しない**。

### 5.4 フレッシュネスと陳腐化

`manifest.json` は Hugging Face のブランチヘッドから取得される。ミラーキャッシュは
短期間、古いコピーを配信する可能性がある。古いマニフェストは真正だが古いため、
チェックは古い seq で「最新」と報告するか、次のチェックを待つ。パブリッシャーの
アップロード順序（成果物が先、マニフェストが最後）により、マニフェストは
ピン留めされたリビジョンでまだ解決できないファイルを決して列挙しないことが保証
される。キャッシュされたファイルは、その sha256 がマニフェストと一致する場合に
のみ受け入れられる。

## 6. ランタイムチャネル（`ai`）

### 6.1 レジストリと RPC サーフェス

| 項目 | 変更 |
| --- | --- |
| `resources.rs` レジストリ行 | `decisions-pack` がチャネル `ai`、トリガー `boot`（サイレントチェック）+ 手動、進捗種別 `ai-models` になる |
| 状態台帳 | `decisions-pack` を `STAMPED_ROWS` に追加し、`<data>/resources/decisions-pack.json` がインストール/チェックのタイムスタンプを記録するようにする |
| 新規コマンド | `ai_pack_status`、`ai_pack_check`、`ai_pack_download`、`ai_pack_cancel`。クリアは `clear_decisions_pack` を再利用する（スタンプ削除まで拡張） |
| 進捗 | `wowsp://download-progress`、種別 `ai-models`、パスごとに 1 ジョブ、`detail` にファイル単位のセグメント |
| webui | 設定 -> リソースカード（6.8 節）、api モジュール、`rpc.ts`、webMock、パリティテスト |

### 6.2 チェック手順

1. ミラーコンテキスト経由でマニフェスト URL を解決し、`manifest.json` を取得する
   （小さなファイル。コールドスタートヘッジを行い、その後
   スティッキーエンドポイントを使う）。
2. Ed25519 署名と正規形を検証し、解析し、seq ラチェットを適用する。
3. `seq` / `treeSha256` を `<cache>/.ai-version.json` と比較する（スタンプは
   `decisions/` の中ではなく隣に置かれ、ツリーハッシュが純粋に保たれる）。差異が
   なければ「最新」と報告する。
4. マニフェストが実行中のビルドでロードできないモデルを宣言している場合
   （6.6 参照）、ダウンロードせずにそのリリースを非互換とマークする。

チェックは起動時に TTL（24 h）の背後でサイレントに行われ、カードからいつでも
利用できる。ダウンロードは決して行わない。ダウンロードはユーザー操作のままである。

### 6.3 ファイル単位のダウンロード

すべてのファイルは `kind = "ai-models"` で `download_hub::transfer` を利用する:

- 候補はミラーコンテキストから来る（Hugging Face プロバイダー、マニフェストの
  ピン留めリビジョン）。ミラープレフィックスの付与は決して適用されない。
- `expected_sha256` = マニフェストのハッシュ、`min_bytes = max_bytes = size`、
  `total_hint = size`、ファイル単位のパート名で `resume = true`。
- あるファイルが失敗した場合、そのファイルについてのみ次のエンドポイントへ
  フォールバックする。パスはすでに検証済みのバイト列をステージングツリーに保持
  する。
- 進捗はパス全体の集計バイト数（`base_received`/`base_total`）に加えて
  `detail: {file, index, files}` を報告する。キャンセルはハブの標準スコープに
  従う。
- ファイルは `<cache>/.ai-staging/<path>` の下に書き込まれる。すべてのファイルが
  揃って検証されるまで、ライブパックには何も触れない。

### 6.4 インストール前の検証

スワップの前に、ブロッキングタスク内で:

1. ステージングされたファイルに対して `treeSha256` を再計算し、マニフェストと
   比較する（余分なファイル/欠落ファイルがあればパスは失敗する）。
2. 各 `.onnx` ファイルを既存の ONNX Runtime ラッパー経由でロードし、分類する。
   種別、入力幅、出力ヘッドが宣言された `kind`/`featureSet` と一致しなければ
   ならない（fire: 24 x `ENTITY_DIM_V2` x `GLOBAL_DIM_V2`、movement: 17 クラス、
   advice: 属性ルーティングヘッド、torpedo: `TORP_GLOBAL_DIM_V2` グローバル
   ブロック）。
3. 必須モデルが失敗した場合、パスを拒否する。オプションモデル（advice、torpedo）
   は、マニフェストがオプションとマークしている場合に限り、警告付きでドロップして
   よい。プロセス内でキャッシュ済みのロード済みモデルは、再起動まで提供を続ける。

これにより、現在の手動パックでは検出できない「世代違いパック」という失敗モードを
排除できる。コストはスワップ前に数メガバイトを解析することである。

### 6.5 インストール、スタンプ、ロールバック

1. `decisions` を `.decisions-backup` に、ステージングを `decisions` に
   リネームする。
2. `{schema, seq, version, revision, treeSha256, manifestSha256, keyId, installedAt}`
   を持つ `<cache>/.ai-version.json` を書き込む。
3. フレッシュネス台帳の行を記録する。成功したらバックアップを削除する。
4. いずれかの失敗（スワップ、スタンプ、台帳）ではバックアップを復元してコマンドを
   失敗させる。キャンセルされたパスは古いパックに何も触れない。

したがって、検証の失敗、パスのクラッシュ、ユーザーによるキャンセルのいずれでも、
常に最後の正常なパックへフォールバックする。カードは `decisions` が存在すると
「クリア」を提供する。ロード済みセッションは再起動まで維持される（既存の挙動）。

### 6.6 特徴量契約

モデルファイルは、Python の学習スクリプトを写した Rust の featurizer と結合して
いる。マニフェストの `featureSet` 値が契約である:

| モデル | 種別 | 特徴量セット（v1） | 必須 |
| --- | --- | --- | --- |
| fire_model.onnx | fire 2 ヘッド（24 エンティティの deep sets） | `fire-v2` | はい |
| move_model.onnx | 17 クラスの移動セクター | `move-v2` | はい |
| advice_fire_model.onnx | 属性ルーティングされたアドバイスヘッド | `advice-e24` | いいえ |
| torpedo_model.onnx | 3 ヘッドの魚雷モデル | `torpedo-e26d` | いいえ |

アプリは、すべての必須モデルの特徴量セットがサポート対象に含まれ、すべての
オプションモデルのセットがサポート対象か存在しない場合にのみ、リリースを
受け入れる。featurizer の変更は、Rust の featurizer を変更するのと同じ PR でセット名を
バンプするので、古いアプリが新しい重みに誤ったテンソルを与えることは決してない。

### 6.7 LOS ラスターとリソースパック

LOS ラスターはリソースパック内のマップジオメトリからベイクされる。パックのマップ
GLB が変わると（ゲームバージョンのバンプ）、古いラスターは古い地形を記述したままに
なる。マニフェストの任意の `resTreeSha256` は、ラスターのベイク対象となったパック
ツリーを記録する。アプリはそれをインストール済みパックのスタンプと比較し、不一致の
場合はモデルをインストールするが LOS ファイルはスキップし（既存のマップ単位の
ルックアップはラスター欠落をすでに許容している）、ユーザーにリソースパックを先に
更新するよう伝える。パブリッシャーはパック公開後に LOS をベイクし、同じ
ツリーハッシュを記録する。

### 6.8 UI、i18n、モバイル

- 設定 -> リソースカードに次の項目が加わる: 現在のバージョン（published-at と
  ツリーハッシュの接尾辞）、存在/サイズ/sha プレフィックス付きのモデル別行、LOS
  カバレッジ（`x/known maps`）、合計サイズ、チェック/ダウンロード/キャンセル
  ボタン、再起動のヒント、ミラーラダーグループ（7.6 節）。
- i18n: 既存の 13 個の `settings.resourcesDecisions*` キーが、8 つの設定ロケール
  （en-US、zh-CN、zh-TW、ja-JP、ko-KR、fr-FR、es-ES、ru-RU）にわたってチェック/
  ダウンロード/進捗/バージョン/LOS カバレッジの文字列で拡張される。正しさの限界は
  `scripts/check_i18n.py` が決める。
- モバイルも同じチャネルを使う（ONNX Runtime はすでにデフォルト機能である）。
  スリム APK はオンデマンドでモデルをダウンロードする。ベースラインをインストーラー/
  APK に同梱することは後の選択肢である（第 10 節、PR4）。
- `ai` 機能なしのビルド（ポータブルフレーバー）は ONNX Runtime をリンクしない。
  チャネルは非表示または利用不可として表示され、ロード不能なモデルを決して
  ダウンロードしない。

### 6.9 失敗モード

| 失敗 | 挙動 |
| --- | --- |
| ミラーに到達できない / マニフェストが 4xx-5xx | チェックは失敗し、現在のパックが提供を続け、理由がログに記録されてカードに表示される |
| 署名が不正 / seq の後退 | ハード失敗。インストールなし、未検証コンテンツへのフォールバックなし |
| ファイルの sha 不一致 | その候補は破棄され、次のエンドポイントが試される。すべて失敗すればパスは失敗する |
| モデルのロード/種別/幅の不一致 | スワップ前にパスを拒否。古いパックを復元 |
| LOS が別のリソースパックツリーにマップされている | モデルはインストールされ、LOS は説明付きの警告とともにスキップされる |
| ディスクフル / キャンセル | ステージングはクリーンアップされるか再開用に保持される。ライブパックには触れない |
| アプリが更新され、特徴量セットがバンプされた | 古いモデルはインストールされたまま残るが、互換リリースがインストールされるまで新しいビルドにはロードされない |

## 7. ミラーコンテキスト

### 7.1 現状の課題

`github_mirror.rs` は `github.com`/`api.github.com` しか知らず、
`{prefix}/{full-url}` で書き換える。Hugging Face のミラーは代わりにエンドポイント
のベースを置換し、パスをそのまま保つ。ModelScope は異なるパステンプレートを持つ。
組み込みリストは、アプリ、`Cargo.toml` の shun メタデータ、
`scripts/fetch_models.py`、ウェブサイトのダウンロードページ、webui モック、リレー
CSP に複製されており、ドリフトテストは Cargo のコピーだけである。6 つの
コンシューマー（`update`、`model_pack`、`data_pack`、`mod_catalog`、
`changelog`、`media`）がそれぞれ独自のループを回している。

### 7.2 プロバイダーモデル

新しいモジュール `packages/app/tauri/src/commands/mirror/`:

```rust
pub enum ProviderId { GitHub, HuggingFace, ModelScope }

pub enum Rewrite {
    UrlPrefix,                                  // GitHub: {prefix}/{official_url}
    Endpoint { template: &'static str },        // HF: {base}/{repo}/resolve/{rev}/{path}
                                                // MS: {base}/models/{repo}/resolve/{rev}/{path}
}

pub struct HfResource<'a> {
    pub repo: &'a str,      // "owner/name"
    pub revision: &'a str,  // pinned commit sha (validated as a plain segment)
    pub path: &'a str,      // repository-relative file path (validated segment by segment)
}

pub struct MirrorContext { /* config snapshot, provider ladders, health/last-good cache */ }

impl MirrorContext {
    pub fn candidates(&self, target: Target<'_>) -> Vec<Candidate>;
    pub fn probe(&self, provider: ProviderId) -> Vec<ProbeRow>;
    pub fn sticky(&self, provider: ProviderId) -> Option<Endpoint>;
}
```

ダウンロードハブは引き続き `Vec<String>` のソースを受け取る。プロバイダー解決は
(config, target) の純粋関数である。ダイジェスト/署名ポリシーは各チャネルに残り、
ミラー URL はトランスポートであり決して内容の同一性ではないという不変条件が保た
れる。

### 7.3 URL マトリクス

| プロバイダー | 公式 | ミラー書き換え | プローブ |
| --- | --- | --- | --- |
| GitHub | `https://github.com/langyo/wowsp/releases/download/<tag>/<asset>` | `{ghproxy-prefix}/{official-url}` | リポジトリの `releases/latest` ページ（既存） |
| Hugging Face | `https://huggingface.co/{repo}/resolve/{rev}/{path}` | `{endpoint}/{repo}/resolve/{rev}/{path}`（例: `https://hf-mirror.com/...`） | 小さなファイルをピン留め: `{endpoint}/{repo}/resolve/{rev}/manifest.json`、HEAD または `Range: bytes=0-1023`、200/206 を許容 |
| ModelScope（将来） | `https://www.modelscope.cn/models/{repo}/resolve/{rev}/{path}` | エンドポイント置換、同一テンプレート | HEAD `resolve/{rev}/manifest.json` |

Hugging Face の API エンドポイント（`/api/models/...`）はダウンロード経路に決して
現れない。プローブがメタデータを必要とする場合はピン留めされたファイルを使う。
匿名 API のバケットはリゾルバーバケットよりはるかに厳しいためである。

### 7.4 選択、ヘルス、ヘッジング

- 候補の順序はプロバイダーごとのポリシーである: GitHub は既存の
  ユーザーエンドポイント -> 公式ルート -> 組み込みの順を維持し、Hugging Face は
  ユーザーエンドポイント -> 組み込み -> 公式ルート（中国本土優先）を使う。設定
  パネルは公式、組み込み、ユーザーの行を、現在の GitHub ラダーと同じ形で表示する。
- **コールドスタート**: 設定された候補（公式 + 組み込み）に対して、開始をずらし
  ながら小さなファイルのリクエストをプローブ/ヘッジする。最初に検証された応答が
  勝ち、敗者はキャンセルされる。これにより、中国本土のユーザーが常に払うことになる
  現在の「公式が先、8-15 s 待ってからフォールバック」という挙動を避けられる。
- **パス/プロバイダーごとのスティッキーエンドポイント**: 候補が応答したら、残りの
  パス（すべてのファイル）はまずそれを使う。失敗時はコミット済みオフセットから
  ラダー内でフェイルオーバーする（ハブの挙動）。
- **ヘルスキャッシュ**: エンドポイントごとの最後の結果、レイテンシ、短い失敗
  クールダウンを、セッションスコープに加えてプロバイダーごとの永続化された
  ラストグッドエンドポイント（appdata 内、ユーザー向け設定ではない）として保持
  する。ユーザー起点のプローブはクールダウンを解除する。
- 大きなファイルの転送はハブ既存のレース/フェイルオーバーを引き続き使う。
  コンテキストはソースの順序付けだけを行う。

### 7.5 設定と IPC

`network-config.toml` に、追加式の任意フィールドが加わる（ほかと同じ camelCase）:

```toml
githubMirrors = ["https://ghfast.top"]
huggingfaceMirrors = ["https://hf-mirror.com", "https://hf-mirror.example"]
```

- ベースエンドポイントのみ（スキーム必須、https のみ、クエリ/フラグメントなし、
  末尾スラッシュ除去、8 エントリ以下、重複排除）。公式ルートは暗黙であり、決して
  保存されない。
- `githubMirrors` の意味は変更しない。レガシーの単一 `githubMirror` 文字列は
  引き続きその先頭に折り込まれる。
- 将来の `providerMirrors` マップは、古い綴りを壊すことなくプロバイダー別
  フィールドを置き換えられる。
- IPC: `mirror_ladder(provider)` と `mirror_probe(provider)` はプロバイダー
  タグ付き DTO を返す。旧 GitHub 名のコマンドは 1 リリースの間、薄いラッパーとして
  残り、webui/api のパリティテストがきれいに切り替わる。
- webui はプロバイダーごとの `useMirrorLadder(provider)` フックと共有のラダー/
  プローブコンポーネントを抽出する。GitHub グループは更新ページに残り、
  Hugging Face グループはモデルカードの隣に置かれる。

### 7.6 エンドポイントカタログとドリフト検査

追跡対象の単一のソース・オブ・トゥルース: `res/config/mirror-endpoints.json`
（プロバイダー -> 公式エンドポイント + 組み込みエンドポイントリスト + プローブ対象
種別）。Rust は `include_str!` でこれを埋め込む。Python（`fetch_models.py`）、
ウェブサイト、リレー CSP の許可リストは、CI と `just lint` に接続された新しい
`scripts/check_mirror_endpoints.py` によってこれを消費するか、これに対して検査
される —— 現在 Cargo の shun メタデータだけがテストされている状況を置き換える。
`res/config/upstream-endpoints.json`（トランスポートヘルスカタログ）は新しい
ホストを獲得し、プロキシ/直接のフォールバックとアップストリームヘルスページが
それらを知るようになる。

### 7.7 中国での観測挙動（2026-11-08、メンテナのネットワーク）

| 対象 | 結果 |
| --- | --- |
| `https://huggingface.co/api/models/...` | 接続タイムアウト（直接ルートは使用不可） |
| `https://hf-mirror.com/api/models/...` | 200、コミット sha を含む完全な Hub API JSON |
| `hf-mirror.com/<repo>/resolve/main/<file>` | 307 -> `/api/resolve-cache/models/<repo>/<sha>/<file>` -> 200、`Accept-Ranges: bytes` |
| ピン留めコミットの resolve | 200 |
| ミラー経由の LFS/Xet ファイル | 302 -> 署名付き `cas-bridge.xethub.hf.co` URL -> 200/206（ミラーは blob のバイト列を保存しない） |
| `www.modelscope.cn/models/<repo>/resolve/master/<file>` | 200 JSON、独立した中国 CDN |

これが、中国本土ユーザー向けのデフォルトの Hugging Face ラダーが組み込みミラー
先頭・公式最後である理由であり、ランタイムが `huggingface.co` の到達性に決して
依存しない理由である。

### 7.8 ミラーの注意点

- サードパーティミラーはベストエフォートの公開サービスであり、正式な SLA や規約は
  ない（hf-mirror.com はコミュニティプロジェクト、ModelScope の再配布条件と
  クォータは未検証）。これらはトランスポートにすぎない。すべてのバイトは
  署名/sha256 で検証され、エンドポイントはユーザーが設定できる。
- 大きなファイルは、署名付きリダイレクトの後に Hugging Face の CDN から配信される
  場合がある。チャネルはコミットをピン留めし sha256 を検証するため、古いファイルや
  誤ったファイルは失敗し、決して受け入れられない。
- 署名付き CDN URL は失効する（約 1 時間）。ダウンローダーはそれらをキャッシュ
  せず、403/失効時に再解決する。
- クライアントにトークンが埋め込まれることは決してない。公開リポジトリのみである。

## 8. 互換性、セキュリティ、不変条件

- **凍結済みのアプリ更新チャネルは不変**: `v*` アップデーター、その shun
  メタデータ、そのダイジェストフローはこのウェーブでは変更されない。
- **リソースパックは不変**: 引き続き GitHub の `res-latest` で、デルタと署名付き
  ダイジェストを使用。ミラーコンテキストは候補の生成方法だけを変える（GitHub では
  同一の順序と URL）。
- **旧クライアントは影響を受けない**: 既存のクライアントは decisions パックを
  ダウンロードしないため、新しいチャネルは互換性の義務を追加しない。リソースパック
  のワイヤーフォーマットは再フォーマットされない。
- **設定の互換性**: 新しい TOML フィールドは任意であり、古いビルドでは無視される。
  設定を修復するダウングレードはそれらを削除し（文書化済み）、アプリは次回の
  アップグレードでデフォルトを再追加する。
- **セキュリティ不変条件**: バージョンとダイジェストの真実は公式のみ。ミラーは
  トランスポート。取得した公式アンカーは拘束力を持つ。実行可能ペイロードは
  フェイルクローズド。ツリー内に秘密情報なし。ONNX ファイルはスワップ前に検証
  される（種別/幅）。
- **脅威モデル**: `docs/en/designs/threat-model.md` と比較すること。新しい攻撃面
  はモデルチャネル（署名で保護された、転送中は未署名の公開コンテンツ）と
  サードパーティミラーエンドポイント（読み取り専用トランスポート）である。

## 9. リスクと緩和策

| リスク | 緩和策 |
| --- | --- |
| ゲーム由来の LOS/属性データを公開再配布する（ライセンス） | 現在の公開パックの前例を維持する。`NOTICE.md` の来歴。第 11 節の決定 2 |
| サードパーティミラーが消滅または敵対化する | 署名 + sha256 検証。ユーザー設定可能なエンドポイント。公式ルートは候補として残る |
| Hugging Face のレート制限 / ポリシー変更 | インストールあたり 46〜120 リクエストで、匿名リゾルバーの予算をはるかに下回る。マニフェストファースト設計。リトライは `RateLimit`/`Retry-After` を尊重する |
| Hugging Face が小さなファイルを Xet に切り替える | ダウンローダーはリダイレクトと Range/再開に追随する。もしそうなったら、組み込みエンドポイントを出荷する前にエンドツーエンドで検証する |
| 特徴量のドリフト（重み vs Rust featurizer） | 明示的な `featureSet` 契約。アプリ側の検証。featurizer の変更はセットをバンプする |
| LOS/ゲームバージョンの不一致 | `resTreeSha256` の比較。プロンプト付きで LOS をスキップ |
| 古いミラーマニフェスト | 認証済みコンテンツ + seq ラチェット。パブリッシャーのアップロード順序。次のチェックで再試行 |
| 未署名/悪意あるマニフェスト | フェイルクローズド。ピン留めされた Ed25519 鍵。クリアテキストのフォールバックなし |
| 公開が誤ってトークンを漏洩させる | `HF_TOKEN` は環境/CI シークレットからのみ。リポジトリ規則に従ったプリコミット grep |
