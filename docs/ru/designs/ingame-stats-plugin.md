# Плагин внутриигровой статистики — проектирование точной телеметрии

> **Статус**: эксперимент завершён (2026-09-28); готов к реализации.
> Документ-компаньон для наложения: слоем отображения остаётся прозрачное
> окно; этот плагин — внутриигровой источник данных, который делает порядок
> наложения точным при любой конфигурации, включая эксклюзивный полноэкранный
> режим.

## Предыстория и цели

Наложение текущего боя сегодня выводит геометрию таблицы команд TAB путём
захвата экрана (`overlay/capture.rs`, `overlay_detect.rs`) и опрашивает
`GetAsyncKeyState(VK_TAB)` с интервалом 30 мс. Это работает, но:

- захват экрана — самый хрупкий слой (исключения DRM/захвата, HDR,
  мульти-DPI, особенности оконного и полноэкранного режимов);
- опрос клавиш не может отличить «Tab зажат» от «Tab введён в боевой чат»;
- порядок строк выводится из статического состава плюс эвристики потоплений.

Внутриигровой мод, работающий поверх официальной **Mods API** Wargaming
(канал PnFMods, без инъекций, без записи в память), может наблюдать состояние
боя изнутри клиента и передавать его WoWSP через файловый мост. Мод
**ничего не отрисовывает** — отображением остаётся прозрачное наложение, —
поэтому подход не несёт того бремени сопровождения UI под каждую версию
игры, которое похоронило ранние идеи «рендеринга в игре».

Цель: сделать «телеметрия мода > вывод по захвату экрана > статический
порядок» цепочкой приоритетов для данных наложения, управляемой новым
режимом состава `"plugin"` в `overlay_config.toml`.

## Что доказал эксперимент

Проверено на Steam-ASIA 15.8.0 (сборка 13187581) и 360-CN 15.8.1 (сборка
13243917), по несколько боёв на каждом; артефакт-пробник находится в
`packages/ingame-plugin/src/Main.py` (навсегда сообщает о себе как
`0.1.0`; итерации живут только в истории git):

| Возможность | Механизм | Задержка / примечания |
| --- | --- | --- |
| Мод загружается на обоих реалмах | `res_mods/<bin>/PnFModsLoader.py` (маркер нулевого размера) + `PnFMods/<Mod>/Main.py`, `API_VERSION = 'API_v1.0'` | сосуществует с модами Aslain |
| Инъектируемые модули API | `events, ui, utils, battle, callbacks, dataHub, constants` — инъектируемые загрузчиком глобальные переменные; их `import` завершается ошибкой (белый список); никогда не затеняйте их | встроенные функции тоже ограничены белым списком: `globals()`/`eval` недоступны |
| Состав и идентификация | `battle.getPlayersInfo()` → name / accountDBID / shipParamsId / isBot / realm | записи — это `SafeClass`: индексация работает, dict-протокол — нет; на ранней загрузке итерируйте защитно (контейнер ненадолго не является dict) |
| Атрибуция потоплений | `isAlive` переключается, опрос каждые 1 с | проверено 1:1 против строк журнала `typeDeath` самой игры, отставание ≤1 с, на 4 боях |
| Прочность в реальном времени и обнаружение | `dataHub.getEntityCollections('avatar')` → `entity[CC.health]` (`.value/.max/.isAlive`), `entity[CC.relation]` | прочность (HP) противника остаётся 0/0 до обнаружения — тот же туман войны, что и в собственной таблице игры; скачок 0→значение сам по себе является событием обнаружения |
| Состояние экрана TAB | события SFM `input.tabModeIn` / `input.tabModeOut` | срабатывает ≤3 мс после клавиши; при Tab в чате **не** срабатывает — целиком устраняет класс ложных срабатываний |
| Изменения состава | `events.onPlayersListUpdated` | 14 событий за один бой |
| Жизненный цикл боя | `sfm.battleLoadingStarted`, `request.showBattle`, `onBattleStart`, `up.exitBattle`, `window.hide(Battle)` | гранулярнее, чем появление/удаление файла tempArenaInfo |

**Недоступно** (и не требуется): компоненты счёта/XP по игрокам на сущностях
avatar не существуют, а путь unbound-стороны
`$datahub.getCollection().getChildByPath('team.ally.sortedAlive')` не имеет
эквивалента на стороне Python (`getCollection` не существует у инъектируемого
dataHub).

**Правило упорядочивания** (подтверждено опытом владельца; согласуется с
именем коллекции `sortedAlive`): таблица TAB сохраняет начальный порядок и
лишь перемещает потопленных игроков в замыкающую «мёртвую» группу.
Следовательно:

```
порядок наложения = порядок техники арены (tempArenaInfo — уже разбирается)
                     с игроками isAlive=false, добавленными заново в порядке
                     потопления
```

является **точным** воспроизведением, а не приближением.

## Ограничения песочницы (добыты тяжёлым трудом — сохранить в руководстве по стилю мода)

- Python — **2.7**; синтаксис держать консервативным (без f-строк;
  существующий пробник намеренно совместим с 2/3).
- у `open()` **нет режима добавления** ('a' возвращает None вместо
  исключения): перезаписывайте файлы целиком из буферов в памяти.
- Отсутствующий файл сначала даёт строку ошибки на стороне движка и лишь
  затем исключение: при загрузке единожды высевайте каждый опрашиваемый
  почтовый ящик (см. посев `manual_refresh.flag`).
- Исключение, покинувшее колбэк, молча убивает мод: оборачивайте всё,
  дедуплицируйте повторяющиеся ошибки перед журналированием.
- `dir()` для инъектируемых модулей возвращает `[]` (обёртки SafeClass):
  поверхность API — только приведённый выше список проверенных имён.
- Существуют два канала загрузчика: классический неподписанный путь
  PnFMods 1.0, который используем мы, и «ModsAPI 2.0» с проверкой подписи
  WG (подписанные моды класса ModStation). Неподписанные моды сообщества
  сосуществуют без проблем; сбои подписи сторонних сборок нас не касаются.

## Архитектура

```
┌─ игровой клиент (песочница Mods API, без сети) ────────────────────┐
│ PnFMods/WoWSPStats/Main.py                                         │
│  · опрос состава (1 с, подтверждение стабильности) → request.json  │
│  · обход сущностей → телеметрия (hp/relation/alive)                │
│  · события SFM → отметки tabMode, отметки жизненного цикла         │
│  · heartbeat.json (фаза port/battle, 1–2 с)                        │
└──────────────┬─────────────────────────────────────────────────────┘
               │ плоские JSON-файлы в собственном каталоге мода
┌──────────────┴─────────────────────────────────────────────────────┐
│ приложение WoWSP (Rust, существующие процессы)                     │
│  · мост чтения/записи (замещает роль компаньона                    │
│    экспериментального пробника; тот же протокол                    │
│    request/response, что установил сторонний                       │
│    референсный плагин)                                             │
│  · механизм упорядочивания: порядок арены + сдвиг потопленных вниз │
│  · режим состава "plugin" в overlay_config                         │
│  · проверка здоровья: разбор profile/python.log в поисках          │
│    строк загрузки/самопроверки мода (api[load] dh=True …)          │
└────────────────────────────────────────────────────────────────────┘
```

Файлы моста (протокол v1, все — в каталоге мода):

```jsonc
// request.json — записывается модом при стабильном составе (и перезаписывается
// при ручном обновлении). Компаньон отвечает строками статистики.
{ "version": 1, "created": 1690000000.0, "session": "1690000000000",
  "manual": false,
  "players": [ { "name": "...", "account_id": 0, "avatar_id": 0,
                 "ship_id": 0 } ] }

// response.json — записывается WoWSP; ревизия обязана монотонно расти в
// рамках сессии; пустой файл (без завершающего перевода строки) означает
// «обрабатывается».
{ "version": 1, "session": "1690000000000", "revision": 3, "busy": false,
  "rows": [ { "name": "...", "wr": 52.3, "pr": 1450, "state": "ok",
              "bf": { "battles": 8213, "ishidden": false } } ] }

// heartbeat.json — перезаписывается каждые 1–2 с; устаревший = мод мёртв
// или игра закрыта.
{ "v": "0.1.0", "t": 1690000000000, "phase": "port" | "battle",
  "players": 17, "revision": 3 }

// журнал телеметрии — полная перезапись ограниченного кольцевого буфера на
// бой; каждое уникальное состояние плюс отметки событий на одной шкале
// времени:
{ "t": 1690000000000, "players": { "<avatarId>": { /* проекция */ } },
  "states": { "<name>": { "hp": "43150.0/43150.0", "relation": "2",
                          "alive": "True" } } }
{ "t": 1690000001000, "ev": "input.tabModeIn" }
{ "t": 1690000004000, "ev": "playersListUpdated" }

// manual_refresh.flag — WoWSP записывает свежую метку epoch-ms для
// запуска повторного запроса; мод потребляет её в пределах окна 10 с.
```

## Продуктовая интеграция

1. **Автоустановка переключателем**: включение внутриигрового источника
   упорядочивания в настройках записывает мод по существующему пути
   `mod_install.rs` / `mod_templates` (маркер `PnFModsLoader.py` — только
   если отсутствует; только собственные файлы; снимок + откат; защита
   «игра закрыта»). Выключение выполняет удаление. Это то «особое»
   поведение регистрации, которое задал владелец: плагин никогда не
   появляется как шаг ручной установки.
2. **Регистрация в Discussions собственного репозитория**: опубликовать
   шаблонную тему-ресурс в `langyo/wowsp/discussions` и сослаться на неё из
   записи `mod-index.json` (`category`, `discussion`, совместимость
   `versions[].game`), чтобы Mod Hub мог также показывать и проверять её,
   как любой другой мод, — происхождение из первых рук, тот же каталогный
   механизм (модель согласия для пробела G8 из mod-hub.md).
3. **Цепочка отката**: телеметрия отсутствует или устарела (пульс старше
   N с, `api[load] dh=False`, игра обновилась и мод сломался) → незаметный
   откат на текущий конвейер вывода. Работоспособность наложения никогда
   не зависит от мода.

## Риски и сопровождение

- **Дрейф WG API** — теперь единственная точка сцепления (без unbound, без
  копий штатных элементов). Поверхность Mods API v1.0 оставалась
  стабильной от 13.x до 15.8; строка самопроверки пробника делает поломку
  заметной и диагностируемой.
- **CN-клиент**: проверено — работает; клиент 360 исполняет тот же
  загрузчик Mods API (его журнал изначально сканирует `PnFModsLoader.py`).
  Следите за изменениями античит-политики CN с каждой мажорной версией.
- **Производительность**: опрос `getPlayersInfo` раз в 1 с + обход
  сущностей хорошо укладывается в бюджет (моды класса TeamHP обходят
  сущности покадрово); никогда не используйте для этого
  `callbacks.perTick`.
- **Рост журнала**: ограниченное кольцо на бой; прикладывайте сегменты к
  повтору, если это полезно для анализа после боя.

## План тестирования

- **Соответствие песочнице**: каждое поставляемое изменение `Main.py`
  валидируется по списку ограничений (разбор py2.7, отсутствие
  заблокированных встроенных функций, отсутствие открытий в режиме
  добавления, защищённые колбэки) плюс `python -m py_compile`.
- **Смоук-тест только в порту** (без боя): запустить игру, постоять в порту
  ~15 с, выйти; проверить наличие `injected names=[…]`, `api[load] dh=True`
  и свежего пульса в `python.log`. Это дешёвый протокол, который
  обеспечивал честность эксперимента, — сохраните его как приёмочный тест
  для установок.
- **Боевые фикстуры**: по одному кооперативному бою на реалм; проверить,
  что журнал содержит снимок состава, ≥1 переключение `alive` по
  потоплению, отметки tabMode, и что строки `typeDeath` в `python.log`
  совпадают с переключениями 1:1.
- **Отработка отката**: остановить приложение (компаньона нет) и
  убедиться, что 180-секундный тайм-аут занятости мода восстанавливается и
  следующий бой по-прежнему отправляет запрос; повредить каталог мода и
  убедиться, что наложение незаметно откатывается на вывод.
