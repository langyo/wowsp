# Распространение ИИ-моделей: канал Hugging Face и многопровайдерные зеркала (проектный контракт)

> Статус: ЧЕРНОВИК — контракт реализации для волны `feat/ai-models`.
> Область: публикация встроенных моделей принятия решений и оценки (весов ONNX,
> таблицы маршрутизации по атрибутам корабля и растров LOS рельефа по каждой
> карте) вместе со скриптами их обучения и развёртывания в публичный репозиторий
> моделей Hugging Face; выдача их клиентам через новый подписанный ресурсный
> канал `ai` с пофайловой загрузкой; и обобщение лестницы зеркал, рассчитанной
> только на GitHub, в учитывающий провайдеров контекст зеркал, общий для
> каждого загружаемого ресурса.
>
> Вне области: замороженный канал обновлений приложения, набор ресурсов
> `res-latest` (он остаётся на GitHub Releases), сам конвейер обучения и
> публикация наборов данных реплеев.

## 1. Проблема и цели

Встроенные модели принятия решений (головы оценки стрельбы и перемещения на
ONNX, модель советов с маршрутизацией по атрибутам, необязательная модель
торпед, таблица маршрутизации и растры линии прямой видимости (LOS) рельефа по
каждой карте) **вообще не имеют канала распространения**. Они существуют как
результаты обучения, игнорируемые git, в `scripts/experiments/out/`;
установленный набор `<cache>/decisions` — это скопированный вручную каталог,
который приложение умеет только инвентаризировать и очищать. Нет ни скрипта
публикации, ни манифеста, ни дайджеста, ни загрузчика, ни штампа версии, ни
гарантии покрытия — сегодня 35 из 96 известных id карт имеют растр LOS, две
установленные модели старше и примерно вдвое меньше текущих экспортов fp32, а
слоты советов и торпед попросту пусты.

При этом приложение уже умеет раздавать более богатый набор: набор ресурсов
`res-latest` публикуется из этого репозитория, зеркалируется через лестницу в
стиле ghproxy для сетей материкового Китая, проверяется по официальным
дайджестам sha256 и применяется атомарно. Канал моделей принятия решений должен
достичь того же инженерного уровня, не наследуя ограничения набора ресурсов
размером 1.3 GB.

Цели:

1. **Один публичный воспроизводимый артефакт.** Каждый релиз модели порождается
   хранящимся в репозитории скриптом из названного коммита репозитория и
   публикуется в публичном репозитории моделей Hugging Face вместе со скриптами
   обучения и развёртывания.
2. **Обновления, независимые от релизов приложения — в пределах контракта
   признаков.** Переобученная модель может дойти до установленных клиентов без
   новой сборки приложения, пока её схема входов/признаков совпадает с
   работающим фичеризатором; изменение схемы по определению является релизом
   приложения.
3. **Целостность до исполнения.** Файлы моделей разбираются и исполняются ONNX
   Runtime, поэтому канал работает по принципу fail-closed: подписанный манифест
   фиксирует sha256 каждого файла и коммит Hugging Face, а неподписанная или
   несовпавшая полезная нагрузка никогда не устанавливается.
4. **Доступность из материкового Китая.** Лестница времени выполнения должна
   работать там, где `huggingface.co` недостижим (проверено из сети
   сопровождающего), не зашивая жёстко ни одного стороннего зеркала.
5. **Один каркас зеркал.** GitHub, Hugging Face и (позже) ModelScope делят один
   учитывающий провайдеров контекст — перезапись кандидатов, пробы, выбор по
   здоровью/закреплению и списки эндпоинтов с проверкой дрейфа — вместо пяти
   копий списка префиксов ghproxy.
6. **Никаких секретов в дереве.** Учётные данные Hugging Face живут в окружении
   или в пользовательском хранилище токенов; никогда в отслеживаемом файле.

## 3. Обзор архитектуры

Три слоя, у каждого одно дело:

```text
  GitHub repo (source of truth)
      |  python scripts/publish_ai_models.py  (hash -> sign -> upload)
      v
  Hugging Face model repo  wowsp-ai  (generated release artifact + scripts snapshot)
      |  signed manifest.json + per-file resolve/<commit-sha>/<path>
      v
  client  commands/ai_pack.rs  --->  commands/mirror/ (MirrorContext)
      |      per-file download via download_hub        GitHub | Hugging Face | ModelScope
      v
  <cache>/decisions  (fire/move/advice/torpedo + attrs + <map>/terrain_los.npz)
```

| Решение | Выбор | Почему |
| --- | --- | --- |
| Источник загрузки | в v1 только Hugging Face (плюс встроенный `hf-mirror.com`); резервный GitHub Release и ModelScope — более поздние провайдеры | один путь публикации для проверки; контекст зеркал делает добавление провайдера дешёвым |
| Якорь доверия манифеста | самоподписанный манифест с использованием существующих закреплённых ключей Ed25519 и храповика `seq` | Hugging Face не предоставляет официального дайджеста на каждый артефакт; канал дайджестов через релей добавил бы шаг развёртывания на каждый релиз модели без дополнительных гарантий |
| Единица передачи | один файл на артефакт, атомарная установка через промежуточный каталог | все файлы < 10 MB; инкрементальные обновления; хаб уже поддерживает прогресс по сегментам, sha256, ограничения, докачку и отмену |
| Выбор зеркала | учитывающая провайдера лестница с хеджированием холодного старта, закреплённым на проход эндпоинтом и охлаждением по здоровью | официальные хосты недостижимы для части аудитории; детерминированный порядок, заданный пользователем, должен сохраняться |
| Набор ресурсов | без изменений, только GitHub | 5.7k файлов, цепочка дельт и дайджесты артефактов GitHub остаются более подходящими |

## 4. Репозиторий Hugging Face

### 4.1 Структура

```text
wowsp-ai/                          public model repository (owner/repo TBD, see 11)
  README.md                        model card: purpose, provenance, metrics, file table, licence
  LICENSE                          Synthetic Source License 1.0 (same as the app repo)
  manifest.json                    signed runtime manifest (section 5)
  NOTICE.md                        game-data provenance and redistribution note (section 4.5)
  onnx/fire_model.onnx
  onnx/move_model.onnx
  onnx/advice_fire_model.onnx
  onnx/torpedo_model.onnx
  onnx-int8/                       optional quantized variants, never installed by default
  attrs/ship_attributes.json
  los/<mapId>/terrain_los.npz
  training/                        generated snapshot: scripts/experiments training/deployment scripts
  SOURCE.json                      {"repo","commit","generatedAt","tool":"scripts/publish_ai_models.py"}
```

`manifest.json` — единственный файл, который приложение трактует как точку
входа канала. Отдельные файлы также скачиваются по отдельности людьми и через
таблицу файлов карточки модели.

### 4.2 Правило размера файла

Каждый файл репозитория остаётся **ниже 10 MB**, чтобы попадать туда обычным
Git-блобом (`/resolve/` возвращает 200 с байтами, без подписанного
перенаправления CDN, без реконструкции xet). Растры LOS сегодня — один файл на
карту (все намного ниже предела); если будущий набор превысит предел на файл,
разделите LOS на пронумерованные пачки, каждая из которых останется ниже него.
Публикатор отказывается от подготовленного файла выше 10 MB и печатает путь
нарушителя.

### 4.3 Модель ревизий

Ревизии Hugging Face — это коммиты; ветки/теги могут двигаться, SHA коммитов —
нет. Поэтому публикация использует два коммита:

1. загрузить файлы артефакта (веса, attrs, LOS, снимок скриптов) -> коммит `A`;
2. загрузить `manifest.json`, `README.md`, `LICENSE`, `NOTICE.md` и
   `SOURCE.json` с `"revision": "A"` внутри манифеста -> коммит `B`.

Приложение получает `manifest.json` из головы ветки (`main`), проверяет его
подпись, а затем скачивает каждый файл из `/{repo}/resolve/{A}/{path}` —
неизменяемого закрепления. Клиент, закешировавший старый манифест, продолжает
использовать старый коммит даже после продвижения `main`. Аннотации (теги
`models-<seq>`) предназначены только для людей.

### 4.4 Процесс публикации и операции

`scripts/publish_ai_models.py` (по образцу `scripts/release_models.py`):

1. собрать входные данные (веса, `ship_attributes.json`, каталог испечённых
   LOS, снимок скриптов из `git archive` названного коммита);
2. посчитать хэш каждого файла, построить подписанный манифест (раздел 5),
   вычислить хэш дерева;
3. загрузить артефакты (коммит A), затем загрузить манифест и документацию
   (коммит B, закреплённый на A);
4. напечатать сводку релиза (seq, sha256 манифеста, коммиты HF, таблица
   файлов). `--dry-run` выполняет каждый локальный шаг без загрузки.

**Учётная запись, токен и создание репозитория.** У Hugging Face нет анонимного
пути записи: публикация требует учётной записи и токена записи. Токен создаётся
в веб-интерфейсе (Settings -> Access Tokens, предпочтительно fine-grained токен,
ограниченный областью записи этого репозитория) и передаётся через `HF_TOKEN`
или стандартное пользовательское хранилище токенов
(`~/.cache/huggingface/token`). Сам репозиторий может быть создан скриптом через
`huggingface_hub.create_repo` (REST `POST /api/repos/create`), через
веб-интерфейс или через необязательный CLI `hf repo create` — все три способа
эквивалентны; **CLI не является обязательным условием**. Публикатор использует
Python API `huggingface_hub`, который также оборачивает официальный GitHub
Action `huggingface/hub-sync`; позже полоса CI может запускать тот же скрипт с
`HF_TOKEN` в качестве секрета репозитория (никогда не отслеживаемого).

**Сетевая реальность.** Запись принимает только `huggingface.co`. Из
материкового Китая этот хост недостижим напрямую (проверено: таймаут
соединения), поэтому локальный запуск публикации требует HTTP(S)-прокси
сопровождающего (`HTTPS_PROXY`), либо публикация выполняется в CI. Зеркало —
прокси только для чтения: чтение во время работы не требует прокси, запись
требует. Проверку после загрузки можно выполнить через зеркало (раздел 7.8).

**Версионирование.** `seq` — строго возрастающий счётчик публикаций, хранимый в
`manifest.json` (публикатор предупреждает, если значение не превышает текущее
опубликованное значение манифеста). `version` — метка времени публикации в UTC,
только для отображения; идентичность содержимого — `treeSha256` (раздел 5.4).

### 4.5 Документация и происхождение

- `README.md` — карточка модели: что делает каждая модель, контракт
  фичеризатора, числа оценки из `scripts/experiments/README.md`
  (auPRC/AUC/ECE/decile lift, где применимо), формы входных/выходных тензоров,
  как воспроизвести, ссылки на точный коммит GitHub и лицензия.
- `SOURCE.json` фиксирует репозиторий, коммит, время генерации и точный хэш
  дерева, так что выпущенный артефакт прослеживается до кода.
- `training/` — **сгенерированный снимок** `scripts/experiments/` (скрипты,
  вспомогательные средства сборки, журнал исследований). Карточка модели
  утверждает, что авторитетный источник — репозиторий GitHub на записанном
  коммите, и что снимок нельзя редактировать на Hugging Face.
- Сырые корпусы реплеев никогда не публикуются: это данные сессий,
  предоставленные пользователями. Карточка модели описывает форму корпуса и
  основу фильтрации/согласия только в обобщённых терминах.
- `NOTICE.md` фиксирует, что растры LOS испечены из опубликованной геометрии
  карт, а таблица атрибутов выведена из игровых данных, и повторяет требование о
  раскрытии Synthetic Source License. Веса обучены на признаках, полученных из
  реплеев. Это тот же класс данных, который уже поставляет публичный канал
  `res-latest`; публикация на втором публичном хосте не меняет лицензию, но
  меняет видимость, поэтому она вынесена явно (раздел 11, решение 2).

### 4.6 Политика синхронизации

GitHub — единственный источник истины. Hugging Face — сгенерированный артефакт
релиза: никаких ручных правок, никакой второй ветки разработки, никакой обратной
синхронизации. Изменение модели начинается в этом репозитории (скрипты обучения
+ артефакты, закоммиченные во входы публикатора), затем сопровождающий запускает
публикатор. Поэтому различия между двумя хостами объясняются происхождением
коммитов, а не параллельным сопровождением.

## 5. Подписанный манифест

### 5.1 Пример

```json
{
  "format": 1,
  "seq": 7,
  "version": "2026-11-08T14:22:03Z",
  "revision": "0123456789abcdef0123456789abcdef01234567",
  "source": { "repo": "langyo/wowsp", "commit": "89abcdef0123456789abcdef0123456789abcdef" },
  "resTreeSha256": "3f2a...",
  "files": [
    { "path": "fire_model.onnx", "sha256": "8ba9...", "size": 2592543,
      "kind": "fire-two-head", "featureSet": "fire-v2", "quant": "fp32" },
    { "path": "move_model.onnx", "sha256": "bc91...", "size": 2652542,
      "kind": "move-sectors-17", "featureSet": "move-v2", "quant": "fp32" },
    { "path": "advice_fire_model.onnx", "sha256": "b98f...", "size": 2595135,
      "kind": "advice-fire-attrs", "featureSet": "advice-e24", "quant": "fp32" },
    { "path": "torpedo_model.onnx", "sha256": "a7e3...", "size": 492411,
      "kind": "torpedo-three-head", "featureSet": "torpedo-e26d", "quant": "fp32" },
    { "path": "ship_attributes.json", "sha256": "2bbd...", "size": 261507 },
    { "path": "50_Gold_harbor/terrain_los.npz", "sha256": "9c1d...", "size": 172432 }
  ],
  "treeSha256": "d41d...",
  "metrics": { "fire": { "auprc": 0.32, "auc": 0.72 } },
  "key_id": "main",
  "sig": "MEUCIQ..."
}
```

### 5.2 Поля

| Поле | Значение |
| --- | --- |
| `format` | версия схемы манифеста (1) |
| `seq` | строго возрастающий счётчик публикаций; приложение отвергает значение ниже последнего установленного |
| `version` | метка времени публикации в UTC, только для отображения |
| `revision` | SHA коммита Hugging Face, который содержит ровно перечисленные файлы |
| `source` | репозиторий GitHub + коммит, из которого был сгенерирован релиз |
| `resTreeSha256` | хэш дерева набора ресурсов, против которого испечены растры LOS (необязателен; отсутствует, когда LOS не поставляется) |
| `files[].path` | путь назначения внутри `<cache>/decisions`; обычный относительный путь, сегменты проверяются (`[A-Za-z0-9._-]`, без `..`, без разделителей внутри сегмента) |
| `files[].sha256` | sha256 точных байтов в нижнем регистре |
| `files[].size` | размер в байтах, используется как нижняя/верхняя граница передачи |
| `files[].kind`, `featureSet`, `quant` | метаданные контракта модели; обязательны для записей `.onnx`, отсутствуют у файлов данных |
| `treeSha256` | идентичность содержимого: sha256 по отсортированным строкам `path\0sha256\n` (та же формула, что у набора ресурсов, поэтому один и тот же инструментарий может хэшировать оба) |
| `metrics` | метаданные отображения, скопированные из отчёта обучения |
| `key_id`, `sig` | слой подписи Ed25519 |

### 5.3 Подпись и защита от отката

Подпись покрывает канонический JSON манифеста **без члена `sig`** — ключи
отсортированы, компактные разделители, UTF-8 — ту же каноническую форму, уже
реализованную в `scripts/catalog_signing.py` и проверяемую приложением против
закреплённых на этапе компиляции открытых ключей
(`packages/app/tauri/res/keys/*.pub`). Подпись переиспользует существующую
церемонию ключей дайджестов релиза; новая пара ключей не вводится.

Приложение проверяет подпись до разбора полей, затем применяет храповик `seq`:
аутентифицированный манифест, чей seq ниже локально сохранённого, отвергается
(защита от повтора/понижения). Таким образом, зеркало в худшем случае может
повторно отдать старый подписанный манифест; подделать его оно не может никогда.
Сбой получения манифеста или недопустимая подпись — жёсткий отказ для этой
проверки: у канала намеренно **нет** запасного пути «принять непроверенный
манифест зеркала», потому что полезная нагрузка — это исполняемое содержимое
модели.

### 5.4 Свежесть и устаревание

`manifest.json` получается из головы ветки Hugging Face. Кеши зеркал могут
короткое время отдавать устаревшую копию; устаревший манифест аутентичен, но
стар, поэтому проверка либо сообщает «актуально» со старым seq, либо ждёт
следующей проверки. Порядок загрузки публикатора (сначала артефакты, манифест
последним) гарантирует, что манифест никогда не называет файлы, которые ещё не
разрешимы на его закреплённой ревизии. Кешированный файл принимается только при
совпадении его sha256 с манифестом.

## 6. Канал времени выполнения (`ai`)

### 6.1 Реестр и поверхность RPC

| Элемент | Изменение |
| --- | --- |
| строка реестра в `resources.rs` | `decisions-pack` становится каналом `ai`, триггер `boot` (тихая проверка) + ручной, вид прогресса `ai-models` |
| реестр состояния | добавить `decisions-pack` в `STAMPED_ROWS`, чтобы `<data>/resources/decisions-pack.json` записывал метки времени установки/проверки |
| новые команды | `ai_pack_status`, `ai_pack_check`, `ai_pack_download`, `ai_pack_cancel`; очистка переиспользует `clear_decisions_pack` (расширенную для удаления штампа) |
| прогресс | `wowsp://download-progress`, вид `ai-models`, одна задача на проход, сегменты по файлам в `detail` |
| webui | карточка Settings -> resources (раздел 6.8), модуль api, `rpc.ts`, webMock, тест паритета |

### 6.2 Последовательность проверки

1. Разрешить URL манифеста через контекст зеркал и получить `manifest.json`
   (небольшой файл; хеджирование холодного старта, затем закреплённый
   эндпоинт).
2. Проверить подпись Ed25519 и каноническую форму; разобрать; применить
   храповик seq.
3. Сравнить `seq` / `treeSha256` с `<cache>/.ai-version.json` (штамп лежит
   рядом с `decisions/`, а не внутри него, поэтому хэш дерева остаётся чистым).
   Нет различий -> сообщить, что актуально.
4. Когда манифест объявляет модели, которые работающая сборка не может загрузить
   (см. 6.6), пометить релиз несовместимым, а не скачивать его.

Проверка тихая при запуске за TTL (24 h) и всегда доступна из карточки. Она
никогда не скачивает; загрузка остаётся действием пользователя.

### 6.3 Пофайловая загрузка

Все файлы проходят через `download_hub::transfer` с `kind = "ai-models"`:

- кандидаты приходят из контекста зеркал (провайдер Hugging Face, закреплённая
  ревизия из манифеста), префиксация зеркала не применяется никогда;
- `expected_sha256` = хэш из манифеста, `min_bytes = max_bytes = size`,
  `total_hint = size`, `resume = true` с именем части на каждый файл;
- сбой одного файла переключает на следующий эндпоинт только для этого файла;
  проход сохраняет уже проверенные байты в промежуточном дереве;
- прогресс сообщает агрегированные байты по проходу
  (`base_received`/`base_total`) плюс `detail: {file, index, files}`; отмена
  следует стандартной области действия хаба;
- файлы пишутся в `<cache>/.ai-staging/<path>`; живой набор не затрагивается,
  пока не присутствует и не проверен каждый файл.

### 6.4 Проверка перед установкой

Перед переключением, в блокирующей задаче:

1. пересчитать `treeSha256` по подготовленным файлам и сравнить с манифестом
   (любой лишний/недостающий файл проваливает проход);
2. для каждого `.onnx`-файла загрузить его через существующие обёртки ONNX
   Runtime и классифицировать: вид, ширины входов и выходные головы должны
   совпадать с объявленными `kind`/`featureSet` (стрельба: 24 x
   `ENTITY_DIM_V2` x `GLOBAL_DIM_V2`; перемещение: 17 классов; советы: голова с
   маршрутизацией по атрибутам; торпеды: глобальный блок `TORP_GLOBAL_DIM_V2`);
3. отвергнуть проход, если обязательная модель не проходит; необязательные
   модели (советы, торпеды) могут быть отброшены с предупреждением, только когда
   манифест помечает их необязательными. Уже загруженная и закешированная в
   процессе модель продолжает обслуживать до перезапуска.

Это устраняет режим отказа «набор неверного поколения», который текущий ручной
набор не может обнаружить, ценой разбора нескольких мегабайт перед
переключением.

### 6.5 Установка, штамп и откат

1. переименовать `decisions` -> `.decisions-backup`, промежуточный каталог ->
   `decisions`;
2. записать `<cache>/.ai-version.json` с `{schema, seq, version, revision,
   treeSha256, manifestSha256, keyId, installedAt}`;
3. записать строку реестра актуальности; при успехе удалить резервную копию;
4. при любом сбое (переключение, штамп, реестр) восстановить резервную копию и
   провалить команду; отменённый проход оставляет старый набор нетронутым.

Поэтому проваленная проверка, упавший проход или отмена пользователем всегда
откатываются к последнему хорошему набору. Карточка предлагает «очистить», как
только `decisions` существует; загруженная сессия держится до перезапуска
(существующее поведение).

### 6.6 Контракт признаков

Файлы моделей связаны с фичеризаторами на Rust, которые повторяют Python-скрипты
обучения. Значения `featureSet` манифеста и есть контракт:

| Модель | Вид | Набор признаков (v1) | Обязательна |
| --- | --- | --- | --- |
| fire_model.onnx | две головы стрельбы (deep sets из 24 сущностей) | `fire-v2` | да |
| move_model.onnx | 17-классовые секторы перемещения | `move-v2` | да |
| advice_fire_model.onnx | голова советов с маршрутизацией по атрибутам | `advice-e24` | нет |
| torpedo_model.onnx | модель торпед с тремя головами | `torpedo-e26d` | нет |

Приложение принимает релиз только тогда, когда набор признаков каждой
обязательной модели входит в поддерживаемый набор, а набор каждой необязательной
модели либо поддерживается, либо отсутствует. Изменение фичеризатора повышает
имя набора в том же PR, который меняет фичеризатор на Rust, поэтому устаревшее
приложение никогда не подаст новым весам не те тензоры.

### 6.7 Растры LOS и набор ресурсов

Растры LOS испекаются из геометрии карт в наборе ресурсов. Когда GLB карт в
наборе меняются (повышение версии игры), старые растры описывают старый рельеф.
Необязательный `resTreeSha256` манифеста фиксирует дерево набора, против
которого испечены растры; приложение сравнивает его со штампом установленного
набора и при несовпадении устанавливает модели, но пропускает файлы LOS
(существующий поиск по карте уже терпит отсутствующие растры) и сообщает
пользователю, что сначала нужно обновить набор ресурсов. Публикатор печёт LOS
после публикации набора и записывает тот же хэш дерева.

### 6.8 UI, i18n и мобильные

- Карточка Settings -> resources получает: текущую версию (published-at и
  суффикс хэша дерева), строки по каждой модели с наличием/размером/префиксом
  sha, покрытие LOS (`x/known maps`), общий размер, кнопки
  проверки/загрузки/отмены, подсказку о перезапуске и группу лестницы зеркал
  (раздел 7.6).
- i18n: существующие 13 ключей `settings.resourcesDecisions*` расширяются
  строками проверки/загрузки/прогресса/версии/покрытия LOS в восьми локалях
  настроек (en-US, zh-CN, zh-TW, ja-JP, ko-KR, fr-FR, es-ES, ru-RU); предел
  корректности — `scripts/check_i18n.py`.
- Мобильные используют тот же канал (ONNX Runtime уже фича по умолчанию).
  Slim-APK скачивает модели по требованию; вложение базовой линии в
  инсталляторы/APK — более поздняя опция (раздел 10, PR4).
- Сборка без фичи `ai` (переносимый вариант) не линкует ONNX Runtime: канал либо
  скрыт, либо показан как недоступный, и никогда не скачивает незагружаемые
  модели.

### 6.9 Режимы отказа

| Отказ | Поведение |
| --- | --- |
| Ни одно зеркало недостижимо / манифест 4xx-5xx | проверка падает, текущий набор продолжает обслуживать, причина записывается в журнал и показывается в карточке |
| Подпись недопустима / регрессия seq | жёсткий отказ; никакой установки, никакого отката к непроверенному содержимому |
| Несовпадение sha файла | этот кандидат отбрасывается; пробуется следующий эндпоинт; проход проваливается, если провалились все |
| Сбой загрузки/вида/ширины модели | проход отвергается до переключения; старый набор восстанавливается |
| LOS отображены на другое дерево набора ресурсов | модели установлены, LOS пропущены с поясняющим предупреждением |
| Диск заполнен / отмена | промежуточные данные очищены или сохранены для докачки; живой набор не тронут |
| Приложение обновлено, имя набора признаков повышено | старые модели остаются установленными, но новой сборкой не загружаются, пока не установлен совместимый релиз |

## 7. Контекст зеркал

### 7.1 Текущая боль

`github_mirror.rs` знает только `github.com`/`api.github.com` и перезаписывает
через `{prefix}/{full-url}`. Зеркала Hugging Face вместо этого подменяют базу
эндпоинта и сохраняют путь; у ModelScope другой шаблон пути. Встроенный список
дублируется в приложении, метаданных shun в `Cargo.toml`,
`scripts/fetch_models.py`, странице загрузки на сайте, webui-моке и CSP релея;
проверке дрейфа подвергается только копия в Cargo. Шесть потребителей (`update`,
`model_pack`, `data_pack`, `mod_catalog`, `changelog`, `media`) каждый крутят
собственный цикл.

### 7.2 Модель провайдеров

Новый модуль `packages/app/tauri/src/commands/mirror/`:

```rust
pub enum ProviderId { GitHub, HuggingFace, ModelScope }

pub enum Rewrite {
    UrlPrefix,                                  // GitHub: {prefix}/{official_url}
    Endpoint { template: &'static str },        // HF: {base}/{repo}/resolve/{rev}/{path}
                                                // MS: {base}/models/{repo}/resolve/{rev}/{path}
}

pub struct HfResource<'a> {
    pub repo: &'a str,      // "owner/name"
    pub revision: &'a str,  // pinned commit sha (validated as a plain segment)
    pub path: &'a str,      // repository-relative file path (validated segment by segment)
}

pub struct MirrorContext { /* config snapshot, provider ladders, health/last-good cache */ }

impl MirrorContext {
    pub fn candidates(&self, target: Target<'_>) -> Vec<Candidate>;
    pub fn probe(&self, provider: ProviderId) -> Vec<ProbeRow>;
    pub fn sticky(&self, provider: ProviderId) -> Option<Endpoint>;
}
```

Хаб загрузки продолжает принимать источники `Vec<String>`: разрешение
провайдера — чистая функция от (config, target). Политика дайджестов/подписей
остаётся в каждом канале, сохраняя инвариант: URL зеркала — это транспорт, а не
идентичность содержимого.

### 7.3 Матрица URL

| Провайдер | Официальный | Перезапись зеркала | Проба |
| --- | --- | --- | --- |
| GitHub | `https://github.com/langyo/wowsp/releases/download/<tag>/<asset>` | `{ghproxy-prefix}/{official-url}` | страница репозитория `releases/latest` (существующая) |
| Hugging Face | `https://huggingface.co/{repo}/resolve/{rev}/{path}` | `{endpoint}/{repo}/resolve/{rev}/{path}` (например, `https://hf-mirror.com/...`) | закрепить небольшой файл: `{endpoint}/{repo}/resolve/{rev}/manifest.json`, HEAD или `Range: bytes=0-1023`, принимать 200/206 |
| ModelScope (позже) | `https://www.modelscope.cn/models/{repo}/resolve/{rev}/{path}` | подмена эндпоинта, тот же шаблон | HEAD `resolve/{rev}/manifest.json` |

Эндпоинты API Hugging Face (`/api/models/...`) никогда не находятся на пути
загрузки; если пробе нужны метаданные, она использует закреплённый файл, потому
что анонимная квота API намного жёстче квоты резолвера.

### 7.4 Выбор, здоровье и хеджирование

- Порядок кандидатов — политика для каждого провайдера: GitHub сохраняет
  существующий порядок «пользовательские эндпоинты -> официальный маршрут ->
  встроенные»; Hugging Face использует «пользовательские эндпоинты -> встроенные ->
  официальный маршрут» (с приоритетом для материкового Китая). Панель настроек
  показывает официальные, встроенные и пользовательские строки в той же форме, что
  у сегодняшней лестницы GitHub.
- **Холодный старт**: пробы/хеджирование запросов небольших файлов по
  настроенным кандидатам со ступенчатыми стартами (официальный + встроенные),
  побеждает первый проверенный ответ; проигравшие отменяются. Это избегает
  текущего поведения «сначала официальный, подождать 8-15 s, затем откатиться»,
  которое пользователи из материкового Китая иначе платили бы всегда.
- **Закреплённый эндпоинт на проход/провайдера**: как только кандидат ответил,
  остаток прохода (все файлы) использует его первым; сбои переключаются внутри
  лестницы с зафиксированного смещения (поведение хаба).
- **Кеш здоровья**: для каждого эндпоинта — последний результат, задержка и
  короткое охлаждение после сбоя; в пределах сессии плюс сохранённый последний
  успешный эндпоинт на каждого провайдера (appdata, не пользовательский конфиг).
  Инициированная пользователем проба сбрасывает охлаждения.
- Передачи больших файлов продолжают использовать существующую
  гонку/аварийное переключение хаба; контекст только упорядочивает источники.

### 7.5 Конфигурация и IPC

`network-config.toml` получает дополнительное необязательное поле (camelCase,
как и остальные):

```toml
githubMirrors = ["https://ghfast.top"]
huggingfaceMirrors = ["https://hf-mirror.com", "https://hf-mirror.example"]
```

- Только базовые эндпоинты (требуется схема, только https, без query/fragment,
  конечный слэш отбрасывается, <= 8 записей, дедупликация); официальный маршрут
  неявен и никогда не сохраняется.
- Семантика `githubMirrors` не тронута; унаследованная одиночная строка
  `githubMirror` продолжает сворачиваться в её голову.
- Будущая карта `providerMirrors` сможет заменить поля по провайдерам, не ломая
  старое написание.
- IPC: `mirror_ladder(provider)` и `mirror_probe(provider)` возвращают DTO с
  меткой провайдера; старые команды с именем GitHub остаются тонкими обёртками
  на один релиз, чтобы тест паритета webui/api переключился чисто.
- webui выделяет хук `useMirrorLadder(provider)` на каждого провайдера и общий
  компонент лестницы/пробы; группа GitHub остаётся на странице обновлений, группа
  Hugging Face — рядом с карточкой модели.

### 7.6 Каталог эндпоинтов и проверки дрейфа

Единый отслеживаемый источник истины: `res/config/mirror-endpoints.json`
(провайдеры -> официальный эндпоинт + список встроенных эндпоинтов + вид цели
пробы). Rust встраивает его через `include_str!`; Python (`fetch_models.py`),
сайт и белые списки CSP релея либо потребляют его, либо проверяются против него
новым `scripts/check_mirror_endpoints.py`, подключённым в CI и `just lint`, —
заменяя текущее положение, когда проверяются только метаданные shun в Cargo.
`res/config/upstream-endpoints.json` (каталог здоровья транспорта) получает
новые хосты, чтобы резервный прокси/прямой путь и страница здоровья апстрима
знали о них.

### 7.7 Наблюдаемое поведение в Китае (2026-11-08, сеть сопровождающего)

| Цель | Результат |
| --- | --- |
| `https://huggingface.co/api/models/...` | таймаут соединения (прямой маршрут непригоден) |
| `https://hf-mirror.com/api/models/...` | 200, полный JSON Hub API, включая sha коммита |
| `hf-mirror.com/<repo>/resolve/main/<file>` | 307 -> `/api/resolve-cache/models/<repo>/<sha>/<file>` -> 200, `Accept-Ranges: bytes` |
| резолв закреплённого коммита | 200 |
| файл LFS/Xet через зеркало | 302 -> подписанный URL `cas-bridge.xethub.hf.co` -> 200/206 (зеркало не хранит байты блобов) |
| `www.modelscope.cn/models/<repo>/resolve/master/<file>` | 200 JSON, независимый CN CDN |

Вот почему лестница Hugging Face по умолчанию для пользователей материкового
Китая — сначала встроенное зеркало, официальный последним, и почему время
выполнения никогда не зависит от достижимости `huggingface.co`.

### 7.8 Оговорки о зеркалах

- Сторонние зеркала — публичные сервисы «по мере возможности» без формального
  SLA или условий (hf-mirror.com — общественный проект; условия
  перераспространения и квоты ModelScope непроверены). Это только транспорты:
  каждый байт проверяется по подписи/sha256, а эндпоинты настраиваются
  пользователем.
- Большие файлы могут отдаваться из CDN Hugging Face после подписанного
  перенаправления; канал закрепляет коммиты и проверяет sha256, поэтому
  устаревший или неверный файл падает, он никогда не принимается.
- Подписанные URL CDN истекают (примерно час); загрузчик вместо их кеширования
  заново разрешает адрес при 403/истечении.
- Токен никогда не встраивается в клиент: только публичные репозитории.

## 8. Совместимость, безопасность и инварианты

- **Замороженный канал обновлений приложения не тронут**: обновлятор `v*`, его
  метаданные shun и его поток дайджестов этой волной не изменяются.
- **Набор ресурсов без изменений**: по-прежнему GitHub `res-latest` с дельтами и
  подписанными дайджестами; контекст зеркал меняет только то, как порождаются
  его кандидаты (идентичные порядок и URL для GitHub).
- **Старые клиенты не затронуты**: ни один существующий клиент не скачивает
  набор решений, поэтому новый канал не добавляет обязательств совместимости;
  проводной формат набора ресурсов не переформатируется.
- **Совместимость конфигурации**: новые поля TOML необязательны и игнорируются
  старыми сборками; откат до более старой версии, который «оздоравливает»
  конфиг, отбрасывает их (это задокументировано), а приложение заново добавляет
  значения по умолчанию при следующем обновлении.
- **Инварианты безопасности**: истина о версии и дайджестах — только официальная;
  зеркала — транспорты; полученный официальный якорь связывает; исполняемые
  полезные нагрузки отказывают закрыто; никаких секретов в дереве; файлы ONNX
  проверяются (вид/ширина) до переключения.
- **Модель угроз**: сверяйтесь с `docs/en/designs/threat-model.md`; новая
  поверхность — канал моделей (публичное содержимое, не подписываемое при
  передаче, но защищённое подписью) и эндпоинты сторонних зеркал (транспорт
  только для чтения).

## 9. Риски и меры смягчения

| Риск | Смягчение |
| --- | --- |
| Публичное перераспространение игровых данных LOS/атрибутов (лицензирование) | сохранить текущий прецедент публичного набора; происхождение в `NOTICE.md`; решение 2 в разделе 11 |
| Стороннее зеркало исчезает или становится враждебным | проверка подписи + sha256; настраиваемые пользователем эндпоинты; официальный маршрут остаётся кандидатом |
| Ограничения частоты / изменения политики Hugging Face | 46-120 запросов на установку, намного ниже анонимного бюджета резолвера; дизайн «сначала манифест»; повторы уважают `RateLimit`/`Retry-After` |
| Hugging Face переводит небольшие файлы на Xet | загрузчик следует перенаправлениям и Range/докачке; если это случится, проверьте сквозным образом перед поставкой встроенного эндпоинта |
| Дрейф признаков (веса против фичеризатора на Rust) | явный контракт `featureSet`; проверка на стороне приложения; изменение фичеризатора повышает набор |
| Несовпадение LOS/версии игры | сравнение `resTreeSha256`; пропуск LOS с подсказкой |
| Устаревший манифест зеркала | аутентифицированное содержимое + храповик seq; порядок загрузки публикатора; повтор при следующей проверке |
| Неподписанный/вредоносный манифест | закрытый отказ; закреплённые ключи Ed25519; никакого отката к открытому тексту |
| Публикация случайно раскрывает токен | `HF_TOKEN` только из окружения/секрета CI; предкоммитный grep по правилам репозитория |

## 11. Открытые решения

1. **Имя владельца/репозитория Hugging Face** (предлагается `langyo/wowsp-ai`,
   публичный). Учётная запись и токен записи принадлежат сопровождающему;
   публикатор может создать репозиторий.
2. **Заявление о перераспространении** игровых растров LOS и таблицы атрибутов:
   публиковать их вместе с весами под существующей лицензией плюс примечание о
   происхождении (рекомендуется, согласуется с публичным набором ресурсов) или
   держать их вне публичного репозитория моделей и отдавать только через
   GitHub-набор приложения.
3. **Объём снимка скриптов обучения**: весь `scripts/experiments/`
   (рекомендуется) или отобранное подмножество; включать ли журнал исследований.
4. **Политика обновлений**: тихая проверка при запуске за TTL 24 h и ручная
   загрузка (рекомендуется) против автоматической загрузки набора ~12 MB;
   выводить ли переключатель «автообновление моделей».
5. **Вторые провайдеры**: ModelScope как полноценный провайдер (нужны учётная
   запись, ключ и проверка условий) и/или резервный источник GitHub Release.
6. **Необязательные артефакты**: поставлять варианты `onnx-int8/` и файлы
   `checkpoint.pt` или только веса (рекомендуется: int8 необязателен,
   контрольные точки не публикуются).
