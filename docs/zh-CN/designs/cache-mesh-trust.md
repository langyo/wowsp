# 缓存网格信任体系 —— 客户端上报、结算与节点后台

> 状态：契约（v1 提案）。本文扩展 `cache-mesh.md`（请先读它），是
> 网格第二波的设计：让**客户端**把查询结果上报进缓存、同时不让任何
> 人投毒，以及监督这一切的运营后台。与其它设计文档一样只维护
> `en` + `zh-CN`。

## 1. 问题

第一波的节点只缓存**自己**抓取的内容（查询代理回源）或从 peer 拉取
的块（CID 一致性校验，但内容诚实性是信任 peer 的）。这浪费了最大的
资产：**成百上千个本来就原生直连上游的游戏客户端** —— 国服玩家在
晚高峰恰好是官方边缘节点最打不动 vortex.wowsgame.cn 的时候访问得最
快。如果客户端把自己抓到的结果上报上来，每个玩家的慢冷查询都会为
之后的所有人预热缓存。

障碍是信任：上报是攻击者可控的输入，声称"这是上游给的"。本文钉死
防投毒设计。

## 2. 设计决策（以及为什么）

考虑过三种机制：

1. **独立上报者仲裁**（"三个不同来源确认"）—— 采纳为 **silver** 层，
   并加细：必须是对**精确内容哈希**的一致同意，来自 ≥3 个不同上报者
   密钥 且 ≥2 个不同 IP 子网（一台机器挂一堆钥匙没用），每个上报者
   声誉不低于门槛，且不存在相互竞争的已结算映射。
2. **服务端自查作为锚** —— 采纳为 **gold** 层，纠正一个前提：
   serverless 平台**可以**抓上游（我们的 Worker 已经在抓）；真正的
   约束是地理可达性与成本，不是平台。因此 **settler**（结算器）到处
   都跑（原生后台任务、Worker cron、Vercel cron），按主机的可达性遥
   测决定何时只剩仲裁一条路。服务端抓取即时结算，优先级高于任何
   仲裁。
3. **昵称 / 军团名白名单** —— 否决作为主机制（冒名、隐私、维护负担）；
   用密码学上报者身份 + 声誉 + 可选的上报闸门（密码 / OAuth / 受信
   列表）替代，私有节点可用受信列表满足同样的诉求。

层级一览（服务信封新增 `tier` 字段）：

| 层 | 含义 | 来源 | 可服务？ |
| --- | --- | --- | --- |
| `gold` | 服务端已验证 | 本节点亲自回源 | 是 |
| `silver` | 仲裁结算 | §4 结算规则 | 是（`x-wowsp-cache: quorum`） |
| `bronze` | 候选 | 1–2 份证明，暂无法验证 | 仅以 `unverified: true` |
| disputed | 争议 | 两个哈希都达到仲裁 | 否 —— 回落上游，后台裁定 |

第一波的块（服务端抓取）按定义是 `gold`；peer 拉取继承源行的层级
（peer 的 silver 仍是 silver）。

## 3. 上报者身份

- 客户端**一次性生成 Ed25519 密钥对**并持久化，向每个上报目标节点
  注册公钥：`POST /api/reports/enroll {pubKey}` →
  `{reporterId}`（密钥指纹，16 hex）。无账号、无昵称、无个人数据。
- 每份报告对 `line || contentHash || fetchedAt || nonce` **签名**，
  节点先验签再做任何事。nonce（节点按上报者单调下发）杀死重放。
- 子网多样性由服务端按报告来源地址计算（v4 取 /24，v6 取 /64），
  **截断存储**（只用于多样性计算与滥用视图 —— 后台永不显示完整地址）。
- 可选上报闸门（面向自部署受众的节点策略）：`open`（默认）|
  `password`（复用节点网关密码）| `trusted`（管理员维护的
  reporterId 白名单 —— 昵称白名单思路的直系后代，军团节点适用）。

## 4. 结算规则

报告为 `{line, contentHash, bodyB64?, fetchedAt, sig, reporterId}`。
候选项按 `(cid, contentHash)` 键控；同一上报者重复证明幂等（一个人
刷不满计数）。

cid → contentHash 映射成为 **silver** 需同时满足：

- ≥ `REPORT_QUORUM`（默认 3）个不同 reporterId 证明该哈希；
- 覆盖 ≥ `REPORT_SUBNET_DIVERSITY`（默认 2）个不同子网；
- 每个被计入的上报者声誉 ≥ −2；
- 各证明的 `fetchedAt` 都落在该条目的 TTL 窗口内（陈旧但曾经为真的
  哈希不能蹭旧时间戳）；
- 同 cid 没有其它哈希正持有 silver/gold。

任一时刻两个哈希同时满足仲裁，cid 翻为 **disputed**：不服务任何一方
（客户端回落上游），行进入后台，settler 优先复核；管理员也可人工
裁定（裁定为某哈希，或全部丢弃）。

声誉事件：之后的服务端抓取证实某哈希 → 每个证明者 +1；证伪 → −2；
分数 < −5 或后台操作 → 封禁。被削减者的证明不再计入仲裁。

## 5. 线上接口

```
POST /api/reports/enroll    {pubKey}                       → {reporterId}
POST /api/reports/submit    （签名报告，体 ≤ 8 MiB，line 须过白名单）
GET  /api/reports/status?cid=<cid>                          → 层级、哈希、计数
GET  /api/blocks/<cid>     信封新增 tier + 证明摘要
```

- 报告的 line 必须通过与查询代理**相同**的 §3.2 主机白名单和上限；
  超限的体直接拒绝，不截断。
- 限流：`REPORT_RATE_PER_HOUR`（默认 60）按 reporterId 与按 IP 双轨；
  429 + retry-after 与全站一致。
- 响应以 `x-wowsp-cache` 标注来源：`hit | miss | peer-hit | quorum |
  unverified`。客户端在诊断行展示 `quorum`/`unverified`；
  `unverified` 只做展示级（用户主动刷新永远走直连链）。

## 6. 结算器（settler）

- **原生**：后台任务 `WOWSP_SERVER_SETTLER`（默认开）—— 每几分钟
  对最热的未结算 cid + 最老的争议直接回源复核（复用 §3.1 代理内核）。
- **Worker**：cron 触发器（10 分钟；赞助者 cron 的既有模式），每次
  运行有预算上限；记录按主机的可达性。边缘连续 24 h 不可达的主机停
  止服务端结算 —— 仲裁成为唯一路径，后台明示这一点。
- **Vercel**：`vercel.json` cron（Hobby 每天一次 —— 仲裁是主力；
  Pro 可以更高）。
- 结算器的每次抓取同时是声誉预言机（§4）。

## 7. 客户端行为（上报侧）

- 直连链（§6.2 回退链，或任何第一方上游抓取）**成功**后——绝不是
  缓存命中的响应，`x-wowsp-cache` 头防止自回环——客户端把结果上报
  给自己的首个缓存服务器：注册（每节点一次），签名 + 提交，后台任务
  发了就算，≤ 8 MiB，仅 2xx JSON 体，静默失败。
- 上报匿名（§3）：载荷就是公开上游服务的内容，按公开请求行编址。
- 设置页的缓存卡片在网格开关旁用一句话披露上报行为。

## 8. 节点后台（/erp 升级）

现有 hikari 控制台（packages/console：飞书 OAuth → 签名会话 →
白名单）增加 `缓存网格` 区块，升级为**节点后台**；反馈/ERP 视图
保持官方独占：

- **总览** —— 按层级的块数、争议队列深度、上报者统计、按主机的
  settler 可达性（近 24 h 成功率）、按来源的服务速率。
- **上报者** —— 每个 reporterId 一行：首末次出现、截断子网摘要、
  接受/结算/证伪/削减计数、声誉分；操作：降权 / 封禁 / 解封；子网
  级 收紧（该子网有效仲裁阈值 +1）。
- **候选与争议** —— 争议 cid 及每个竞争哈希的证明明细；操作：
  立即复核（立刻触发 settler）/ 人工裁定 / 全部丢弃。
- **Peer 治理** —— 已宣告 peer 列表，隐藏/拉黑，宣告日志（谁、从
  哪个子网、何时宣告了什么）。
- **策略** —— 仲裁/多样性/限流阈值、上报闸门模式、上报开关；变更
  即节点变量，控制台覆写存管理 KV 行。

自部署节点的认证（那边没有飞书）：首启铸造**控制台令牌**进数据目录
并只打印一次（反馈查询凭证的同一模式）；登录视图粘贴令牌 → 铸同样的
签名会话。支持 `CONSOLE_TOKENS`（多管理员）经环境变量。官方节点
保留飞书 OAuth。自部署的反馈视图默认隐藏，除非
`FEEDBACK_SELFHOST=1` —— 即便开了也只是**链接**到官方控制台：反馈
管线按设计写入官方节点的飞书租户（没人看的自部署收件箱不值得开）。

## 9. 滥用预算摘要

| 向量 | 约束 |
| --- | --- |
| 投毒块 | 需要 3 把钥匙 + 2 个子网 + 全员声誉 ≥ −2，且一次服务端复核即可证伪；争议映射永不服务 |
| 女钥匙 | 子网多样性 + 每子网上报者上限 + 注册限流（10/h/IP） |
| 声誉养殖 | 只在服务端证实的结算上得分；+1 的唯一来源是 settler |
| 重放 | 签名信封内按上报者单调的 nonce |
| 内存/存储 | 候选随条目 TTL + 宽限过期；超限体拒绝；争议 48 h 过期 |
| 后台接管 | 与今日 /erp 相同的会话 + 白名单模型；自部署令牌服务端铸造 |
| 流量 | 按上报者且按 IP 的报告限流；体上限；settler 预算 |

## 10. 上线步骤

- T1 —— relay-core 报告/仲裁/声誉策略 + Worker（候选 `ReportLedger`
  SQLite DO + R2 体 + 接口 + settler cron）+ 原生（同一策略跑在
  SQLite 上 + settler 任务）+ Vercel（Upstash）。上报默认**关闭**
  （`REPORTS_ENABLED`），官方节点观察期后再开。
- T2 —— 客户端：密钥对 + 注册 + 直连成功后签名上报。
- T3 —— 控制台升级（网格视图、自部署令牌认证、反馈自部署链接态）。
- T4 —— 文档波（指南 + 本文件 zh-CN 同步）。
