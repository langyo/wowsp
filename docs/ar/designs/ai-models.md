# توزيع نماذج الذكاء الاصطناعي: قناة Hugging Face ومرايا متعددة المزوّدين (عقد التصميم)

> الحالة: مسودة — عقد التنفيذ لموجة `feat/ai-models`.
> النطاق: نشر نماذج القرار/التسجيل المدمجة (أوزان ONNX، وجدول توجيه سمات
> السفن، والخرائط النقطية لخط بصر التضاريس (LOS) لكل خريطة) مع سكربتات
> التدريب/النشر الخاصة بها إلى مستودع نماذج عام على Hugging Face؛
> وتقديمها للعملاء عبر قناة موارد `ai` موقَّعة جديدة بتنزيلات لكل ملف؛
> وتعليم سلّم المرايا الخاص بـ GitHub وحده إلى سياق مرايا واعٍ بالمزوّد
> تشترك فيه كل الموارد القابلة للتنزيل.
>
> خارج النطاق: قناة تحديث التطبيق المجمَّدة، وحزمة الموارد `res-latest`
> (تبقى على GitHub Releases)، وخط أنابيب التدريب نفسه، ونشر مجموعة بيانات
> الريبلاي.

## 1. المشكلة والأهداف

لا تملك نماذج القرار المدمجة (رؤوس تسجيل الإطلاق/الحركة في ONNX، ونموذج
النصائح الموجَّه بالسمات، ونموذج الطوربيد الاختياري، وجدول التوجيه، والخرائط
النقطية لخط بصر التضاريس لكل خريطة) **أي قناة توزيع على الإطلاق**. فهي
موجودة كمخرجات تدريب مُهمَلة في git تحت `scripts/experiments/out/`؛ وحزمة
`<cache>/decisions` المثبَّتة مجلد منسوخ يدويًا لا يستطيع التطبيق إلا جرده
ومسحه. لا يوجد سكربت ناشر، ولا بيان، ولا بصمة، ولا مُنزِّل، ولا طابع إصدار،
ولا ضمان تغطية — فاليوم تحمل 35 من معرّفات الخرائط الـ96 المعروفة خريطة LOS
نقطية، والنموذجان المثبَّتان أقدمان ونصف حجم تصديرات fp32 الحالية تقريبًا،
وخانتا النصائح/الطوربيد فارغتان ببساطة.

وفي الوقت نفسه يعرف التطبيق أصلًا كيف يقدّم حزمة أغنى: فحزمة الموارد
`res-latest` تُنشر من هذا المستودع، وتُقدَّم عبر مرايا على نمط ghproxy
لشبكات البرّ الرئيسي الصيني، وتُتحقَّق مقابل بصمات sha256 الرسمية، وتُطبَّق
ذريًّا. وينبغي لقناة نماذج القرار أن تبلغ المعيار الهندسي نفسه دون أن ترث
قيود حزمة الموارد البالغة 1.3 GB.

الأهداف:

1. **أصل عام واحد قابل لإعادة الإنتاج.** كل إصدار نماذج يُولَّد بسكربت
   مضمَّن في المستودع من إيداع مسمّى في المستودع، ويُنشر إلى مستودع نماذج
   عام على Hugging Face مع سكربتات التدريب والنشر الخاصة به.
2. **تحديثات مستقلة عن إصدارات التطبيق — ضمن عقد سمات.** يمكن لنموذج
   مُعاد تدريبه أن يصل إلى العملاء المثبَّتين دون بناء تطبيق جديد ما دام
   مخطط المدخلات/السمات لديه يطابق مُشكّل السمات العامل؛ وتغيير المخطط هو
   إصدار تطبيق بالتعريف.
3. **السلامة قبل التنفيذ.** تُحلَّل ملفات النموذج وتُنفَّذ بواسطة ONNX
   Runtime، لذا تفشل القناة مغلقة: يثبّت البيان الموقَّع تجزئة sha256 لكل
   ملف وإيداع Hugging Face، ولا تُثبَّت أبدًا حمولة غير موقَّعة أو غير
   مطابقة.
4. **الوصول من البرّ الرئيسي.** يجب أن يعمل سلّم التشغيل حيث يتعذّر الوصول
   إلى `huggingface.co` (متحقَّق منه على شبكة المشرف) دون تثبيت أي مرآة طرف
   ثالث واحدة تثبيتًا صلبًا.
5. **إطار مرايا واحد.** تتشاطر GitHub وHugging Face و(لاحقًا) ModelScope
   سياقًا واحدًا واعيًا بالمزوّد — إعادة كتابة المرشّحات، والاستبار،
   واختيار الصحة/الالتصاق، وقوائم نقاط نهاية مفحوصة الانحراف — بدلًا من خمس
   نسخ من قائمة بادئات ghproxy.
6. **لا أسرار في الشجرة.** تعيش بيانات اعتماد Hugging Face في البيئة أو في
   مخزن رموز المستخدم؛ ولا تعيش أبدًا في ملف متعقَّب.

## 2. الوضع الحالي

| المجال | اليوم | الأثر |
| --- | --- | --- |
| نشر النماذج | لا شيء | لا يمكن للنماذج أن تصل إلى المستخدمين إلا بنسخ يدوي |
| الحزمة المثبَّتة | `<LOCALAPPDATA>/WoWSP/decisions`، منسوخة يدويًا | متقادمة/جزئية؛ بلا طابع؛ والنماذج من جيل خاطئ لا يمكن كشفها |
| تحميل النماذج | سلّم `decision_serve`: البيئة → خانة الحزمة → مخرجات التطوير؛ و`ship_attrs` يستخدم جدول `include_str!` وقت الترجمة | تغيير جدول التوجيه يحتاج إصدار تطبيق؛ وتعليق «الحزمة تتجاوز الجدول المضمَّن» غير منفَّذ |
| حزمة الموارد | `res-latest` على GitHub + سلسلة الدلتا + بصمات موقَّعة من المُرحّل | ناضجة؛ تبقى كما هي |
| سلّم المرايا | قائمة مضيفين خاصة بـ GitHub وحدها مع تسلسل بادئات ghproxy؛ ونسخ في Rust، وبيانات Cargo الوصفية، وPython، والموقع، وبديل webui الوهمي، وسياسة CSP للمُرحّل | لا يستطيع أن يكون واجهة أمامية لـ `huggingface.co`؛ والانحراف لا يُفحص إلا في نسخة واحدة |
| الجوال | ONNX Runtime ميزة افتراضية، فبنيات Android/iOS تشحن ONNX؛ وحزمة القرارات غير مضمَّنة | سيستفيد الجوال من القناة نفسها |
| صف السجل | `decisions-pack`، والقناة فارغة، والمُشغِّل `manual` | لا أزرار فحص/تنزيل، ولا مدخل في سجل الحداثة |

إذن هذه الموجة **تُنشئ قناة**؛ وهي لا تُرحّل قناة قائمة.

## 3. نظرة عامة على البنية

ثلاث طبقات، لكل منها مهمة واحدة:

```text
  GitHub repo (source of truth)
      |  python scripts/publish_ai_models.py  (hash -> sign -> upload)
      v
  Hugging Face model repo  wowsp-ai  (generated release artifact + scripts snapshot)
      |  signed manifest.json + per-file resolve/<commit-sha>/<path>
      v
  client  commands/ai_pack.rs  --->  commands/mirror/ (MirrorContext)
      |      per-file download via download_hub        GitHub | Hugging Face | ModelScope
      v
  <cache>/decisions  (fire/move/advice/torpedo + attrs + <map>/terrain_los.npz)
```

| القرار | الخيار | السبب |
| --- | --- | --- |
| مصدر التنزيل | Hugging Face وحده في v1 (مع `hf-mirror.com` المدمج)؛ وتراجع GitHub Release وModelScope مزوّدان لاحقًا | مسار نشر واحد للتحقق؛ وسياق المرايا يجعل إضافة مزوّد رخيصة |
| مرتكز ثقة البيان | بيان موقَّع ذاتيًا بمفاتيح Ed25519 المثبَّتة القائمة وسقّاطة `seq` | لا تكشف Hugging Face أي بصمة رسمية لكل أصل؛ وقناة بصمات عبر المُرحّل ستضيف خطوة نشر لكل إصدار نماذج دون أي ضمان إضافي |
| وحدة النقل | ملف واحد لكل أصل، وتثبيت ذري من منطقة التجهيز | كل الملفات < 10 MB؛ وتحديثات تزايدية؛ والمركز يدعم أصلًا تقدّم كل مقطع، وsha256، والحدود، والاستئناف، والإلغاء |
| اختيار المرآة | سلّم واعٍ بالمزوّد مع تحوّط البدء البارد، ونقطة نهاية لاصقة لكل تمريرة، وتهدئة صحية | المضيفات الرسمية متعذّرة على جزء من الجمهور؛ ويجب الحفاظ على الترتيب الحتمي الذي يسرده المستخدم |
| حزمة الموارد | دون تغيير، GitHub وحدها | 5.7k ملف وسلسلة الدلتا وبصمات أصول GitHub تبقى الأنسب |

## 4. مستودع Hugging Face

### 4.1 التخطيط

```text
wowsp-ai/                          public model repository (owner/repo TBD, see 11)
  README.md                        model card: purpose, provenance, metrics, file table, licence
  LICENSE                          Synthetic Source License 1.0 (same as the app repo)
  manifest.json                    signed runtime manifest (section 5)
  NOTICE.md                        game-data provenance and redistribution note (section 4.5)
  onnx/fire_model.onnx
  onnx/move_model.onnx
  onnx/advice_fire_model.onnx
  onnx/torpedo_model.onnx
  onnx-int8/                       optional quantized variants, never installed by default
  attrs/ship_attributes.json
  los/<mapId>/terrain_los.npz
  training/                        generated snapshot: scripts/experiments training/deployment scripts
  SOURCE.json                      {"repo","commit","generatedAt","tool":"scripts/publish_ai_models.py"}
```

`manifest.json` هو الملف الوحيد الذي يعامله التطبيق كنقطة دخول القناة. كما أن
الملفات الفردية قابلة للتنزيل منفردةً من قِبل البشر وعبر جدول الملفات في
بطاقة النموذج.

### 4.2 قاعدة حجم الملف

يبقى كل ملف في المستودع **أدنى من 10 MB** ليهبط ككتلة Git عادية (يعيد
`/resolve/` الرمز 200 مع البايتات، بلا إعادة توجيه موقَّعة إلى CDN، وبلا
إعادة بناء xet). وخرائط LOS النقطية ملف واحد لكل خريطة اليوم (كلها أدنى
بكثير من الحد)؛ وإذا تجاوزت حزمة مستقبلية الحد لكل ملف، فقسّم LOS إلى حزم
مرقّمة تبقى كل منها دونه. ويرفض الناشر أي ملف مجهَّز يتجاوز 10 MB ويطبع
المسار المخالف.

### 4.3 نموذج المراجعة

مراجعات Hugging Face هي إيداعات؛ فالفروع/الوسوم قد تتحرك، أما تجزئات الإيداع
فلا. لذا يستخدم النشر إيداعين:

1. رفع ملفات الأصل (الأوزان، وattrs، وLOS، ولقطة السكربتات) → الإيداع `A`؛
2. رفع `manifest.json` و`README.md` و`LICENSE` و`NOTICE.md` و`SOURCE.json`
   مع `"revision": "A"` داخل البيان → الإيداع `B`.

يجلب التطبيق `manifest.json` من رأس الفرع (`main`)، ويتحقق من توقيعه، ثم
ينزّل كل ملف من `/{repo}/resolve/{A}/{path}` — تثبيت غير قابل للتغيير.
والعميل الذي خزّن بيانًا أقدم يواصل استخدام الإيداع الأقدم حتى بعد تقدّم
`main`. أما التعليقات (وسوم `models-<seq>`) فللبشر فقط.

### 4.4 سير عمل النشر والعمليات

`scripts/publish_ai_models.py` (على نمط `scripts/release_models.py`):

1. جمع المدخلات (الأوزان، و`ship_attributes.json`، ومجلد LOS المحسوب
   مسبقًا، ولقطة السكربتات من `git archive` للإيداع المسمّى)؛
2. تجزئة كل ملف، وبناء البيان الموقَّع (القسم 5)، وحساب تجزئة الشجرة؛
3. رفع الأصول (الإيداع A)، ثم رفع البيان والوثائق (الإيداع B، مثبَّتًا على
   A)؛
4. طباعة ملخّص الإصدار (`seq`، وsha256 البيان، وإيداعات HF، وجدول الملفات).
   و`--dry-run` ينفّذ كل خطوة محلية دون رفع.

**الحساب والرمز وإنشاء المستودع.** لا تملك Hugging Face مسار كتابة مجهول:
فالنشر يحتاج حسابًا ورمز كتابة. ويُنشأ الرمز في واجهة الويب
(Settings -> Access Tokens، ويفضَّل رمز دقيق الحبيبات محصور في نطاق كتابة
هذا المستودع) ويُقدَّم عبر `HF_TOKEN` أو مخزن رموز المستخدم القياسي
(`~/.cache/huggingface/token`). ويمكن للسكربت نفسه إنشاء المستودع عبر
`huggingface_hub.create_repo` (REST `POST /api/repos/create`)، أو عبر واجهة
الويب، أو عبر أداة `hf repo create` الاختيارية — والثلاثة متكافئة؛ **وأداة
CLI ليست شرطًا مسبقًا**. ويستخدم الناشر واجهة `huggingface_hub` في Python،
وهي نفس ما يغلّفه إجراء GitHub الرسمي `huggingface/hub-sync`؛ وقد يشغّل مسار
CI لاحقًا السكربت نفسه مع `HF_TOKEN` سرًّا في المستودع (غير متعقَّب أبدًا).

**واقع الشبكة.** لا يقبل الكتابة إلا `huggingface.co`. ومن البرّ الرئيسي
الصيني يتعذّر بلوغ ذلك المضيف مباشرةً (متحقَّق منه: مهلة اتصال)، لذا يحتاج
النشر المحلي إلى وسيط HTTP(S) الخاص بالمشرف (`HTTPS_PROXY`)، أو يجري النشر
على CI. والمرآة وسيط قراءة فقط: فقراءات التشغيل لا تحتاج وسيطًا، أما الكتابات
فتحتاجه. ويمكن التحقق بعد الرفع عبر المرآة (القسم 7.8).

**الإصدارات.** `seq` عدّاد نشر متزايد بصرامة مخزَّن في `manifest.json`
(وينبّه الناشر إذا لم تتجاوز القيمة تلك الموجودة في البيان المنشور حاليًا).
و`version` هو طابع وقت النشر بتوقيت UTC؛ وهوية المحتوى هي `treeSha256`
(القسم 5.4).

### 4.5 التوثيق والمنشأ

- `README.md` بطاقة نموذج: ما يفعله كل نموذج، وعقد مُشكّل السمات، وأرقام
  التقييم من `scripts/experiments/README.md` (auPRC/AUC/ECE/رفع العُشْر حسب
  الاقتضاء)، وأشكال تنسورات المدخل/المخرج، وكيفية إعادة الإنتاج، وروابط
  الإيداع الدقيق على GitHub، والترخيص.
- `SOURCE.json` يسجّل المستودع والإيداع وزمن التوليد وتجزئة الشجرة الدقيقة،
  فيصير الأصل المنشور قابلًا للتتبّع إلى الشيفرة.
- `training/` **لقطة مولَّدة** من `scripts/experiments/` (السكربتات،
  ومساعدات البناء، وسجل البحث). وتنصّ بطاقة النموذج على أن المصدر المرجعي هو
  مستودع GitHub عند الإيداع المسجَّل، وأن اللقطة يجب ألا تُحرَّر على
  Hugging Face.
- لا تُنشر مدوّنات الريبلاي الخام أبدًا: فهي بيانات جلسات يساهم بها
  المستخدمون. وتصف بطاقة النموذج شكل المدوّنة وأساس الترشيح/الموافقة بصفة
  إجمالية فقط.
- `NOTICE.md` يسجّل أن خرائط LOS النقطية محسوبة مسبقًا من هندسة الخرائط
  المنشورة وأن جدول السمات مشتق من بيانات اللعبة، ويعيد النص على شرط
  الإفصاح في رخصة Synthetic Source License. والأوزان مدرَّبة من سمات مشتقة
  من الريبلاي. وهذه هي فئة البيانات نفسها التي تشحنها قناة `res-latest`
  العامة أصلًا؛ والنشر على مضيف عام ثانٍ لا يغيّر الترخيص، لكنه يغيّر
  الظهور، لذا يُنبَّه إليه صراحةً (القسم 11، القرار 2).

### 4.6 سياسة المزامنة

GitHub هو المصدر الوحيد للحقيقة. أما Hugging Face فأصل إصدار مولَّد: لا
تحريرات يدوية، ولا فرع تطوير ثانٍ، ولا مزامنة عكسية. يبدأ تغيير النموذج في
هذا المستودع (سكربتات التدريب + الأصول المضمَّنة في مدخلات الناشر)، ثم يشغّل
أحد المشرفين الناشر. لذا تُفسَّر الفروق بين المضيفين بمنشأ الإيداع، لا
بصيانة متوازية.

```json
    { "path": "50_Gold_harbor/terrain_los.npz", "sha256": "9c1d...", "size": 172432 }
  ],
  "treeSha256": "d41d...",
  "metrics": { "fire": { "auprc": 0.32, "auc": 0.72 } },
  "key_id": "main",
  "sig": "MEUCIQ..."

```

### 5.2 الحقول

| الحقل | المعنى |
| --- | --- |
| `format` | إصدار مخطط البيان (1) |
| `seq` | عدّاد نشر متزايد بصرامة؛ ويرفض التطبيق أي قيمة أدنى من آخر قيمة ثبّتها |
| `version` | طابع وقت النشر بتوقيت UTC، للعرض فقط |
| `revision` | تجزئة إيداع Hugging Face التي تحوي الملفات المدرجة بالضبط |
| `source` | مستودع GitHub + الإيداع الذي وُلِّد الإصدار منه |
| `resTreeSha256` | تجزئة شجرة حزمة الموارد التي حُسبت خرائط LOS مقابلها (اختياري؛ يغيب إذا لم يُشحن أي LOS) |
| `files[].path` | مسار الوجهة داخل `<cache>/decisions`؛ مسار نسبي عادي، ومقاطعه متحقَّق منها (`[A-Za-z0-9._-]`، بلا `..`، وبلا فواصل داخل المقطع) |
| `files[].sha256` | sha256 بأحرف صغيرة للبايتات الدقيقة |
| `files[].size` | الحجم بالبايت، ويُستخدم حدًّا أدنى/أقصى للنقل |
| `files[].kind`، `featureSet`، `quant` | بيانات وصفية لعقد النموذج؛ مطلوبة لمدخلات `.onnx`، وغائبة لملفات البيانات |
| `treeSha256` | هوية المحتوى: sha256 على أسطر `path\0sha256\n` المرتّبة (بصيغة مطابقة لحزمة الموارد، فتستطيع الأدوات ذاتها تجزئة الاثنين) |
| `metrics` | بيانات وصفية للعرض منسوخة من تقرير التدريب |
| `key_id`، `sig` | طبقة توقيع Ed25519 |

### 5.3 التوقيع ومقاومة التراجع

يغطي التوقيع JSON القانوني للبيان **من دون العضو `sig`** — مفاتيح مرتّبة،
وفواصل مضغوطة، وUTF-8 — وهو الشكل القانوني نفسه المنفَّذ أصلًا في
`scripts/catalog_signing.py` والمتحقَّق منه في التطبيق مقابل مفاتيح عامة
مثبَّتة وقت الترجمة (`packages/app/tauri/res/keys/*.pub`). ويعيد التوقيع
استخدام مراسم مفتاح بصمة الإصدار القائمة؛ ولا يُدخَل زوج مفاتيح جديد.

يتحقق التطبيق من التوقيع قبل تحليل الحقول، ثم يطبّق سقّاطة `seq`: يُرفض أي
بيان موثَّق يكون `seq` فيه أدنى من المخزَّن محليًا (حارس ضد إعادة
الإرسال/التخفيض). وهكذا تستطيع المرآة في أسوأ حال أن تعيد تقديم بيان موقَّع
قديم؛ ولا تستطيع أبدًا تزوير واحد. وفشل جلب البيان أو توقيع غير صالح فشلٌ
صلب لهذا الفحص — فالقناة **لا** تملك عمدًا أي تراجع «اقبل بيان مرآة غير
متحقَّق منه»، لأن الحمولة محتوى نماذج قابل للتنفيذ.

### 5.4 الحداثة والتقادم

يُجلب `manifest.json` من رأس فرع Hugging Face. وقد تقدّم ذاكرات المرايا
المؤقتة نسخة متقادمة لفترة قصيرة؛ والبيان المتقادم أصيل لكنه أقدم، فيُبلِغ
الفحص إما «محدَّث» مع `seq` القديم أو ينتظر الفحص التالي. ويضمن ترتيب رفع
الناشر (الأصول أولًا، والبيان أخيرًا) ألا يسمّي البيان ملفات غير قابلة للحل
أصلًا عند مراجعته المثبَّتة. ولا يُقبل ملف مخزَّن إلا عندما تطابق تجزئة
sha256 الخاصة به البيان.

## 6. قناة التشغيل (`ai`)

### 6.1 السجل وسطح RPC

| البند | التغيير |
| --- | --- |
| صف سجل `resources.rs` | يصير `decisions-pack` القناة `ai`، والمُشغِّل `boot` (فحص صامت) + يدوي، ونوع التقدّم `ai-models` |
| سجل الحالة | إضافة `decisions-pack` إلى `STAMPED_ROWS` كي يسجّل `<data>/resources/decisions-pack.json` الطوابع الزمنية للتثبيت/الفحص |
| أوامر جديدة | `ai_pack_status`، و`ai_pack_check`، و`ai_pack_download`، و`ai_pack_cancel`؛ ويعيد المسح استخدام `clear_decisions_pack` (موسَّعًا ليزيل الطابع) |
| التقدّم | `wowsp://download-progress`، ونوع `ai-models`، ومهمة واحدة لكل تمريرة، ومقاطع لكل ملف في `detail` |
| webui | بطاقة Settings -> resources (القسم 6.8)، ووحدة api، و`rpc.ts`، وwebMock، واختبار التكافؤ |

### 6.2 تسلسل الفحص

1. حلّ عنوان URL للبيان عبر سياق المرايا وجلب `manifest.json` (ملف صغير؛
   تحوّط البدء البارد، ثم نقطة النهاية اللاصقة).
2. التحقق من توقيع Ed25519 ومن الشكل القانوني؛ ثم التحليل؛ ثم تطبيق سقّاطة
   `seq`.
3. مقارنة `seq` / `treeSha256` بـ `<cache>/.ai-version.json` (يعيش الطابع
   بجوار `decisions/` لا داخله، فتبقى تجزئة الشجرة نقية). لا فرق → الإبلاغ
   بأنها الحالية.
4. عندما يعلن البيان نماذج لا تستطيع البنية العاملة تحميلها (انظر 6.6)، وسم
   الإصدار بأنه غير متوافق بدلًا من تنزيله.

الفحص صامت عند الإقلاع خلف مهلة صلاحية (24 ساعة)، ومتاح دائمًا من البطاقة.
وهو لا ينزّل أبدًا؛ ويبقى التنزيل فعلًا من المستخدم.

### 6.3 التنزيل لكل ملف

كل الملفات تمر عبر `download_hub::transfer` مع `kind = "ai-models"`:

- المرشّحات تأتي من سياق المرايا (مزوّد Hugging Face، ومراجعة مثبَّتة من
  البيان)، وبادئة المرآة لا تُطبَّق أبدًا؛
- `expected_sha256` = تجزئة البيان، و`min_bytes = max_bytes = size`،
  و`total_hint = size`، و`resume = true` باسم جزء لكل ملف؛
- فشل ملف واحد يتراجع إلى نقطة النهاية التالية لذلك الملف وحده؛ وتحتفظ
  التمريرة ببايتاتها المتحقَّق منها في شجرة التجهيز؛
- يبلّغ التقدّم عن بايتات مجمَّعة عبر التمريرة (`base_received`/`base_total`)
  مع `detail: {file, index, files}`؛ ويتبع الإلغاء نطاق المركز القياسي؛
- تُكتب الملفات تحت `<cache>/.ai-staging/<path>`؛ ولا يمسّ شيء الحزمة الحية
  حتى يكون كل ملف حاضرًا ومتحقَّقًا منه.

### 6.4 التحقق قبل التثبيت

قبل التبديل، وفي مهمة حاجزة:

1. إعادة حساب `treeSha256` على الملفات المجهَّزة ومقارنتها بالبيان (أي ملف
   زائد/غائب يُفشل التمريرة)؛
2. لكل ملف `.onnx`، تحميله عبر أغلفة ONNX Runtime القائمة وتصنيفه: يجب أن
   يطابق النوع وعروض المدخلات والرؤوس الخارجة `kind`/`featureSet` المعلنَين
   (الإطلاق: 24 x `ENTITY_DIM_V2` x `GLOBAL_DIM_V2`؛ الحركة: 17 صنفًا؛
   النصائح: رأس موجَّه بالسمات؛ الطوربيد: كتلة عامة `TORP_GLOBAL_DIM_V2`)؛
3. رفض التمريرة إذا فشل نموذج مطلوب؛ ويجوز إسقاط النماذج الاختيارية
   (النصائح، الطوربيد) مع تحذير فقط عندما يوسمها البيان اختيارية. والنموذج
   المحمَّل المخزَّن أصلًا في العملية يواصل الخدمة حتى إعادة التشغيل.

بهذا يُقضى على نمط فشل «الحزمة من جيل خاطئ» الذي لا تستطيع الحزمة اليدوية
الحالية كشفه، بثمن تحليل بضعة ميغابايتات قبل التبديل.

### 6.5 التثبيت والطبع والتراجع

1. إعادة تسمية `decisions` → `.decisions-backup`، والتجهيز → `decisions`؛
2. كتابة `<cache>/.ai-version.json` بالحقول `{schema, seq, version, revision, treeSha256, manifestSha256, keyId, installedAt}`؛
3. تسجيل صف سجل الحداثة؛ وحذف النسخة الاحتياطية عند النجاح؛
4. عند أي فشل (التبديل، أو الطبع، أو السجل) استعد النسخة الاحتياطية وأفشل
   الأمر؛ والتمريرة الملغاة تترك الحزمة القديمة سليمة.

لذا فالتحقق الفاشل أو التمريرة المنهارة أو إلغاء المستخدم يرجع دائمًا إلى
آخر حزمة سليمة. وتعرض البطاقة «مسح» بمجرد وجود `decisions`؛ وتبقى الجلسة
المحمَّلة حتى إعادة التشغيل (السلوك القائم).

### 6.6 عقد السمات

ملفات النماذج مقترنة بمُشكّلات السمات في Rust التي تحاكي سكربتات التدريب في
Python. وقيم `featureSet` في البيان هي العقد:

| النموذج | النوع | مجموعة السمات (v1) | مطلوب |
| --- | --- | --- | --- |
| fire_model.onnx | إطلاق ثنائي الرأس (مجموعات عميقة من 24 كيانًا) | `fire-v2` | نعم |
| move_model.onnx | قطاعات حركة من 17 صنفًا | `move-v2` | نعم |
| advice_fire_model.onnx | رأس نصائح موجَّه بالسمات | `advice-e24` | لا |
| torpedo_model.onnx | نموذج طوربيد ثلاثي الرؤوس | `torpedo-e26d` | لا |

لا يقبل التطبيق إصدارًا إلا عندما تكون مجموعة سمات كل نموذج مطلوب ضمن
مجموعته المدعومة، ومجموعة كل نموذج اختياري إما مدعومة أو غائبة. وتغيير
مُشكّل السمات يرفع اسم المجموعة في الـPR نفسه الذي يغيّر مُشكّل السمات في
Rust، فلا يستطيع تطبيق متقادم أن يغذّي أوزانًا جديدة تنسوراتٍ خاطئة.

### 6.7 خرائط LOS النقطية وحزمة الموارد

تُحسب خرائط LOS النقطية من هندسة الخرائط في حزمة الموارد. وعندما تتغيّر
ملفات GLB للخرائط في الحزمة (رفع إصدار اللعبة)، تصف الخرائط القديمة تضاريس
قديمة. ويسجّل `resTreeSha256` الاختياري في البيان شجرة الحزمة التي حُسبت
الخرائط مقابلها؛ ويقارنه التطبيق بطابع الحزمة المثبَّتة، وعند عدم التطابق
يثبّت النماذج لكنه يتخطى ملفات LOS (فالبحث القائم لكل خريطة يتحمّل أصلًا
غياب الخرائط) ويطلب من المستخدم تحديث حزمة الموارد أولًا. ويحسب الناشر LOS
بعد نشر الحزمة ويسجّل تجزئة الشجرة نفسها.

### 6.8 الواجهة وi18n والجوال

- تكتسب بطاقة Settings -> resources في الإعدادات: الإصدار الحالي (وقت النشر
  ولاحقة تجزئة الشجرة)، وصفوفًا لكل نموذج بالحضور/الحجم/بادئة sha، وتغطية
  LOS (`x/known maps`)، والحجم الإجمالي، وأزرار الفحص/التنزيل/الإلغاء،
  وتلميحة إعادة التشغيل، ومجموعة سلّم المرايا (القسم 7.6).
- i18n: تُوسَّع مفاتيح `settings.resourcesDecisions*` الـ13 الموجودة بنصوص
  الفحص/التنزيل/التقدّم/الإصدار/تغطية LOS عبر لغات الإعدادات الثماني (en-US،
  وzh-CN، وzh-TW، وja-JP، وko-KR، وfr-FR، وes-ES، وru-RU)؛ وحدّ الصحة هو
  `scripts/check_i18n.py`.
- يستخدم الجوال القناة نفسها (ONNX Runtime ميزة افتراضية أصلًا). ويُنزّل APK
  النحيف النماذج عند الطلب؛ أما تضمين خط أساس في المثبِّتات/حزم APK فخيار
  لاحق (القسم 10، PR4).
- البناء بلا ميزة `ai` (النسخة المحمولة) لا يربط ONNX Runtime: فالقناة إما
  مخفية أو معروضة كغير متاحة، ولا تنزّل أبدًا نماذج غير قابلة للتحميل.

## 7. سياق المرايا

### 7.1 الوجع الحالي

لا يعرف `github_mirror.rs` إلا `github.com`/`api.github.com` ويعيد الكتابة
بـ `{prefix}/{full-url}`. أما مرايا Hugging Face فتستبدل أساس نقطة النهاية
وتُبقي المسار؛ ولـ ModelScope قالب مسار مختلف. والقائمة المدمجة مكرَّرة في
التطبيق، وفي بيانات shun الوصفية في `Cargo.toml`، وفي
`scripts/fetch_models.py`، وفي صفحة تنزيل الموقع، وفي بديل webui الوهمي،
وفي سياسة CSP للمُرحّل؛ ولا يُفحص الانحراف إلا في نسخة Cargo. وستة مستهلكين
(`update`، و`model_pack`، و`data_pack`، و`mod_catalog`، و`changelog`،
و`media`) يدور كل منهم في حلقته الخاصة.

### 7.2 نموذج المزوّد

وحدة جديدة `packages/app/tauri/src/commands/mirror/`:

```rust
pub enum ProviderId { GitHub, HuggingFace, ModelScope }

pub enum Rewrite {
    UrlPrefix,                                  // GitHub: {prefix}/{official_url}
    Endpoint { template: &'static str },        // HF: {base}/{repo}/resolve/{rev}/{path}
                                                // MS: {base}/models/{repo}/resolve/{rev}/{path}
}

pub struct HfResource<'a> {
    pub repo: &'a str,      // "owner/name"
    pub revision: &'a str,  // pinned commit sha (validated as a plain segment)
    pub path: &'a str,      // repository-relative file path (validated segment by segment)
}

pub struct MirrorContext { /* config snapshot, provider ladders, health/last-good cache */ }

impl MirrorContext {
    pub fn candidates(&self, target: Target<'_>) -> Vec<Candidate>;
    pub fn probe(&self, provider: ProviderId) -> Vec<ProbeRow>;
    pub fn sticky(&self, provider: ProviderId) -> Option<Endpoint>;
}
```

يواصل مركز التنزيل أخذ مصادر `Vec<String>`: فحلّ المزوّد دالة نقية من
(الإعدادات، والهدف). وتبقى سياسة البصمة/التوقيع في كل قناة، بما يحفظ الثابت
القائل إن رابط المرآة نقلٌ، وليس هوية محتوى أبدًا.

### 7.3 مصفوفة URL

| المزوّد | الرسمي | إعادة كتابة المرآة | الاستبار |
| --- | --- | --- | --- |
| GitHub | `https://github.com/langyo/wowsp/releases/download/<tag>/<asset>` | `{ghproxy-prefix}/{official-url}` | صفحة `releases/latest` للمستودع (القائمة) |
| Hugging Face | `https://huggingface.co/{repo}/resolve/{rev}/{path}` | `{endpoint}/{repo}/resolve/{rev}/{path}` (مثل `https://hf-mirror.com/...`) | تثبيت ملف صغير: `{endpoint}/{repo}/resolve/{rev}/manifest.json`، بطلب HEAD أو `Range: bytes=0-1023`، وقبول 200/206 |
| ModelScope (لاحقًا) | `https://www.modelscope.cn/models/{repo}/resolve/{rev}/{path}` | استبدال نقطة النهاية، والقالب نفسه | HEAD `resolve/{rev}/manifest.json` |

نقاط نهاية واجهة Hugging Face (`/api/models/...`) ليست أبدًا على مسار
التنزيل؛ وإذا أراد استبارٌ بيانات وصفية فإنه يستخدم ملفًا مثبَّتًا، لأن حصة
واجهة API المجهولة أضيق بكثير من حصة المُحلِّل.

### 7.4 الاختيار والصحة والتحوّط

- ترتيب المرشّحات سياسة لكل مزوّد: يُبقي GitHub على الترتيب القائم (نقاط
  النهاية المُهيَّأة من المستخدم، ثم المسار الرسمي، ثم النقاط المدمجة)؛
  ويستخدم Hugging Face نقاط النهاية المُهيَّأة من المستخدم، ثم النقاط المدمجة،
  ثم المسار الرسمي (البرّ الرئيسي أولًا). وتعرض لوحة الإعدادات الصفوف الرسمية
  والمدمجة وصفوف المستخدم بالشكل نفسه الموجود في سلّم GitHub اليوم.
- **البدء البارد**: استبار/تحوّط طلبات الملفات الصغيرة عبر المرشّحات
  المُهيَّأة ببدايات متدرّجة (الرسمي + المدمجة)، ويفوز أول ردّ متحقَّق منه؛
  وتُلغى الخاسرة. هذا يتجنّب سلوك «الرسمي أولًا، انتظر 8-15 ث، ثم تراجع»
  الحالي الذي كان مستخدمو البرّ الرئيسي سيدفعونه دائمًا لولا ذلك.
- **نقطة نهاية لاصقة لكل تمريرة/مزوّد**: بمجرد أن يجيب مرشّح، تستخدمه بقية
  التمريرة (كل الملفات) أولًا؛ وتتجاوز الإخفاقات داخل السلّم من الإزاحة
  الملتزمة بها (سلوك المركز).
- **ذاكرة الصحة**: لكل نقطة نهاية، آخر نتيجة، والكمون، وتهدئة فشل قصيرة، في
  نطاق الجلسة إضافة إلى نقطة نهاية سليمة أخيرة محفوظة لكل مزوّد (في بيانات
  التطبيق، لا في إعدادات المستخدم). واستبار يبدأه المستخدم يمسح فترات
  التهدئة.
- تحتفظ عمليات نقل الملفات الكبيرة بسباق/تجاوز المركز القائم؛ والسياق لا
  يفعل إلا ترتيب المصادر.

### 7.5 الإعدادات وIPC

يكتسب `network-config.toml` حقلًا إضافيًا اختياريًا (بأسلوب camelCase كبقية
الحقول):

```toml
githubMirrors = ["https://ghfast.top"]
huggingfaceMirrors = ["https://hf-mirror.com", "https://hf-mirror.example"]
```

- نقاط نهاية أساسية فقط (المخطط مطلوب، وhttps وحده، وبلا استعلام/جزء،
  وتُجرَّد الشرطة المائلة الختامية، و≤ 8 مدخلات، ومزالة التكرار)؛ والمسار
  الرسمي ضمني ولا يُخزَّن أبدًا.
- دلالات `githubMirrors` لا تُمس؛ ويواصل نص `githubMirror` المفرد القديم
  الانطواء في رأسها.
- خريطة `providerMirrors` مستقبلية يمكن أن تحل محل الحقول لكل مزوّد دون كسر
  التهجئة القديمة.
- IPC: `mirror_ladder(provider)` و`mirror_probe(provider)` يعيدان DTOs
  موسومة بالمزوّد؛ وتبقى الأوامر القديمة المسمّاة بـ GitHub أغلفة رقيقة
  لإصدار واحد كي ينقلب اختبار تكافؤ webui/api بنظافة.
- يستخرج webui خطّافًا `useMirrorLadder(provider)` لكل مزوّد ومكوّنًا مشتركًا
  للسلّم/الاستبار؛ وتبقى مجموعة GitHub في صفحة التحديثات، ومجموعة Hugging
  Face بجوار بطاقة النموذج.

### 7.6 دليل نقاط النهاية وفحوص الانحراف

مصدر حقيقة واحد متعقَّب: `res/config/mirror-endpoints.json` (المزوّدون → نقطة
النهاية الرسمية + قائمة نقاط النهاية المدمجة + نوع هدف الاستبار). ويثبّته
Rust بـ `include_str!`؛ ويستهلكه Python (`fetch_models.py`) والموقع وقوائم
السماح في CSP للمُرحّل، أو يُفحص مقابلَه بسكربت جديد
`scripts/check_mirror_endpoints.py` موصولًا بـ CI و`just lint` — بدلًا من
الوضع الحالي الذي لا يُفحص فيه إلا بيانات shun الوصفية في Cargo. ويكتسب
`res/config/upstream-endpoints.json` (دليل صحة النقل) المضيفين الجدد كي
تعرفهم آلية التراجع بين الوسيط/المباشر وصفحة صحة المنبع.

### 7.7 السلوك المرصود في الصين (2026-11-08، شبكة المشرف)

| الهدف | النتيجة |
| --- | --- |
| `https://huggingface.co/api/models/...` | مهلة اتصال (المسار المباشر غير قابل للاستخدام) |
| `https://hf-mirror.com/api/models/...` | 200، JSON كامل لواجهة Hub بما فيه تجزئة الإيداع |
| `hf-mirror.com/<repo>/resolve/main/<file>` | 307 → `/api/resolve-cache/models/<repo>/<sha>/<file>` → 200، و`Accept-Ranges: bytes` |
| حلّ إيداع مثبَّت | 200 |
| ملف LFS/Xet عبر المرآة | 302 → عنوان URL موقَّع على `cas-bridge.xethub.hf.co` → 200/206 (المرآة لا تخزّن بايتات الكتلة) |
| `www.modelscope.cn/models/<repo>/resolve/master/<file>` | 200 JSON، وشبكة CDN صينية مستقلة |

لهذا كان سلّم Hugging Face الافتراضي لمستخدمي البرّ الرئيسي يضع المرآة
المدمجة أولًا والرسمي أخيرًا، ولهذا لا يعتمد التشغيل أبدًا على إمكان الوصول
إلى `huggingface.co`.

### 7.8 تحذيرات المرايا

- مرايا الأطراف الثالثة خدمات عامة بأفضل جهد، بلا اتفاقية خدمة (SLA) أو شروط
  رسمية (hf-mirror.com مشروع مجتمعي؛ وشروط إعادة التوزيع وحصص ModelScope غير
  متحقَّق منها). وهي نقل فقط: كل بايت متحقَّق منه بالتوقيع/sha256، ونقاط
  النهاية قابلة للتهيئة من المستخدم.
- قد تُقدَّم الملفات الكبيرة من شبكة CDN الخاصة بـ Hugging Face بعد إعادة توجيه
  موقَّعة؛ والقناة تثبّت الإيداعات وتتحقق من sha256، فيفشل الملف المتقادم أو
  الخاطئ، ولا يُقبل أبدًا.
- عناوين CDN الموقَّعة تنتهي صلاحيتها (نحو ساعة)؛ ويعيد المنزِّل حلّها عند
  403/انتهاء الصلاحية بدلًا من تخزينها.
- لا يُضمَّن أي رمز في العميل أبدًا: المستودعات العامة وحدها.

## 8. التوافق والأمان والثوابت

- **قناة تحديث التطبيق المجمَّدة لا تُمس**: لا تُعدَّل محدِّث `v*` ولا بياناته
  الوصفية shun ولا تدفّق بصماته في هذه الموجة.
- **حزمة الموارد دون تغيير**: ما تزال `res-latest` على GitHub مع الدلتات
  والبصمات الموقَّعة؛ وسياق المرايا لا يغيّر إلا كيفية إنتاج مرشّحاتها
  (ترتيب وعناوين URL متطابقة لدى GitHub).
- **العملاء القدامى غير متأثرين**: لا عميل قائم ينزّل حزمة القرارات، فالقناة
  الجديدة لا تضيف أي التزام توافق؛ وصيغة إرسال حزمة الموارد لا يُعاد
  تنسيقها.
- **توافق الإعدادات**: حقول TOML الجديدة اختيارية وتتجاهلها البناءات الأقدم؛
  والتخفيض الذي يعالج الإعدادات يُسقطها (موثَّق)، ويعيد التطبيق إضافة
  الافتراضيات في الترقية التالية.
- **ثوابت الأمان**: الحقيقة الرسمية وحدها للإصدار والبصمات؛ والمرايا نقل؛
  ومرتكز رسمي مُحرز يُلزِم؛ والحمولات القابلة للتنفيذ تفشل مغلقة؛ ولا أسرار
  في الشجرة؛ وملفات ONNX متحقَّق منها (النوع/العرض) قبل التبديل.
- **نموذج التهديد**: قارن بـ `docs/en/designs/threat-model.md`؛ والسطح الجديد
  هو قناة النماذج (محتوى عام غير موقَّع أثناء النقل محميّ بالتوقيع) ونقاط
  نهاية مرايا الأطراف الثالثة (نقل للقراءة فقط).
